# Lint-clean, fluent Thai prose can still misstate facts — check content fidelity separately from style

Asked to "revise the language" of CRDB full-report §5.1, then specifically to check whether §5.1.5 (the 8 climate services) matched the WP6 service narrative and gap analysis. Running the writing-th linter (once its actual venv path was found — see below) caught real style violations that a careful manual read had missed. But §5.1.5 itself was a different problem: it read as fluent, internally consistent, well-cited Thai institutional prose, and was still wrong in several load-bearing places that no linter or style rule could catch:

- Service 6's stated baseline (an existing ปภ./GISTDA/สสน. early-warning system) directly contradicted the source, which says explicitly there is no existing platform and the service must be built from scratch.
- A percentage framed as "roughly half" (61 of 122) had no supporting count anywhere in the source register — it was 122÷2 with the appearance of a derived finding.
- Per-service reason-code counts (access 56, metadata 34, uncertainty_info 13 assigned to specific services) were actually totals across all 97 items, presented as if they were that one service's own numbers.
- A model was cited under the wrong internal work-package label ("WP6 Loss and Damage Data Model" when WP6 is a different folder entirely; the real model is ch. 4 / WP9), and a headline figure (฿1.62 trillion) was attributed to the wrong study and presented with the wrong scope (a sector case study, when it's actually the national total).
- A "value chain" framing linking all 8 services in sequence existed in no source document — it was invented framing that sounded plausible.

**Root cause**: style-pack lint and manual reading both check the sentence, not the claim. A claim is only checkable against its named or implied source, which requires actually opening that source and comparing. On a report chapter built from many prior working documents (methodology.md, plan-slice.md, the WP6 narrative, the September demand-supply register, an older 10-gap analysis, a loss-and-damage model spec), the drafting process readily blends numbers and framings from different populations or different documents into one fluent paragraph, and nothing about fluent prose signals that blending happened.

**Fix that worked**: when asked a fidelity question, send independent read-only agents (fresh context, no visibility into the drafting reasoning) to re-derive each specific claim from its named source file, not just re-read the draft. Splitting the claims across two agents by type (narrative/framing claims vs. numeric/labeling claims) surfaced non-overlapping real defects — mirrors the dual-Stage-5-review pattern already known from `[[project_crdb_5_3_8_inventory_centred_reanalysis]]` (mechanical rubric + cold reader catch different things). This is expensive (~100-150k tokens per agent) and should be reserved for when a fidelity question is actually asked, not run by default on every paragraph.

**Separate infrastructure note**: the writing-th skill's PostToolUse lint hook is configured to call `.agents/skills/writing-th/.venv`, which does not exist in this repo. The real, working venv is at `.claude/skills/writing-th/.venv`. Until the hook path is fixed, the automatic post-edit lint advisory always errors and must be run manually with the correct path — `.claude/skills/writing-th/.venv/Scripts/python.exe .claude/skills/writing-th/scripts/lint_thai_writing.py <draft> ψ/memory/style/LEXICON_TH.json --scope report`.

**How to apply**: when a user asks "does this match the source" or similar, or when reviewing any drafted section built from multiple prior analysis documents before it's treated as final, don't rely on a passing lint or a careful read — dispatch fresh read-only verification against the named sources, one claim at a time, with file:line citations required in the report back.
