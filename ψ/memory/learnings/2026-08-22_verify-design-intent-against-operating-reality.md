# Lesson: verify a document's stated design against operating reality before citing it as evidence

**Context**: While analyzing DCCE's 2025 M&E Platform (Ditto's Phase 2 report), I cited the report's "Dimension 4: Monitoring, Evaluation and Learning (MEL)" section — a paragraph of design language plus a 0–5 scoring formula — as evidence DCCE "already has a MEL system, it just needs activating." Boss challenged this twice, from two different angles, in the same session:

1. The scoring/evaluation language I quoted was "very generic... could be written by Googling" — true of the philosophy paragraph, though the worked numeric formulas were more specific than that. Either way, a document containing a mechanism's formula is not evidence the mechanism runs — targets have to actually be entered, scores actually computed, for "evaluation" to be happening rather than merely specified.
2. Separately, Dimension 4 turned out to contain zero institutional-arrangement content — no owner, no authority, no routing logic, no legal/budget hook. It's a measurement scaffold, not a governance design. DCCE having *accepted* this document as a deliverable (a procurement fact) doesn't make it *institutionally adequate* (a design fact) — these are different axes and shouldn't be treated as one.

**Pattern to watch for**: when a source document *describes* a process ("the system compares results to targets and adjusts policy accordingly"), that description is evidence of *intent* or *specification*, not evidence of *operation*. The two have to be checked separately, against separate evidence (design docs vs. operational status reports, in this case a later launch-event transcript that confirmed the design was never run).

**How to apply**: before citing a document's stated mechanism as proof something works or exists functionally, ask (a) is there separate evidence this actually ran/runs, and (b) does the design actually contain the institutional/authority layer needed to function, or only the measurement/technical layer. Flag the gap explicitly rather than letting a well-written specification stand in for a working system.

**Related**: this pattern also applied to a second, distinct conflation in the same session — answering "is Research a formal stage in a MEL/MERL governance cycle" using an *activity taxonomy* (what adaptation projects spend money on) instead of a *governance-stage* framework (what steps a cycle formally has). Different axis, same root cause: reaching for the nearest available classification instead of checking it actually answers the question asked.
