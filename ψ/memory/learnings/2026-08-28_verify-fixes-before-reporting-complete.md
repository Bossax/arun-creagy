# Lesson: Verify a claimed fix before reporting it complete

**Context**: Drafting CRDB exec-summary §1.2 via `/writing-th`, revision round 2→3. Told Boss (and the independent reviewer) I had made a term consistent across four occurrences in the section. I had actually fixed 2 of 4 — I ran a scoped edit intended to hit all instances but didn't check. In the same round I also "fixed" a flagged false superlative by substituting a comparison, without tracing what the comparison's reference class actually contained, and produced a claim that was circular (comparing two items to a class consisting only of those same two items).

**Pattern**: A tool call returning success is not evidence that the *intended semantic change* landed everywhere it was supposed to, especially for global text patterns ("make this term consistent," "rename X to Y throughout"). The gap between "the edit tool didn't error" and "the fix is actually complete" is exactly where overclaiming happens.

**Fix that worked**: After the second failure, switched to: (1) make the change with a global/all-occurrences replace rather than by hand at each site, (2) immediately grep for the old pattern with a boundary check (e.g. old-term-not-followed-by-expected-character) and confirm zero matches, (3) only then report the fix as done. For substitutions that add a new comparison or qualifier (not just renaming), explicitly re-derive what the comparison's reference class contains before asserting an extremum/superlative against it.

**Generalizes to**: Any multi-round correction loop — code review fixes, lint-error cleanup, find-and-replace across a document — where a user or reviewer will check your claim of "fixed" against the actual state rather than your report of it. Applies especially when resubmitting to the same reviewer/tests twice in a row: the second failure to fully land a fix reads as worse than the first defect, because it signals the verification step itself is missing, not just that the content was imperfect.
