# Lesson: judge indicators as set members, not solo scope-coverage

**Context**: GGGI NAP AP project, NRM sector reviewer worklist (`ψ/incubate/GGGI/NAP_AP/output/2026-08-17_NRM-reviewer-worklist.md`).

**What happened**: While reviewing activity-indicator pairings for a rubric-driven M&E indicator crosswalk, I repeatedly recommended cutting indicators that only measured part of a multi-habitat or multi-ecosystem activity's scope (e.g. a marine-only Ocean Health Index attached to a cross-ecosystem bio-indicator activity; a mangrove-specific indicator implicitly read as excluding coral; a wetland-specific cooperation-network indicator attached to a generic cross-ecosystem CSR activity). The reviewer (human) caught two instances via inline comments; I found a third myself by applying the same corrected logic proactively.

**The error**: treating "this indicator does not by itself cover the activity's full scope" as sufficient grounds to cut it. The correct framing: a broad-scope activity needs a *set* of habitat/domain-specific indicators, not one indicator that does everything. A partial-coverage indicator should only be cut if something better replaces it — cutting it when no broader alternative exists just deletes real information for no gain.

**A related but distinct trap**: explicit mention of one sub-topic in a guideline/measure's text (e.g. "mangrove restoration") is not proof the activity's scope is narrowed to that sub-topic exclusively — it may just be flagging a sub-topic that's commonly omitted from generic framing (e.g. "marine and coastal" often defaults to reef/open-sea and forgets mangrove). Don't infer exclusive scope from emphasis alone; check the actual measure/guideline text for whether it's additive or exclusive.

**How to apply**: When evaluating indicator-to-activity fit for any multi-domain activity (cross-sector, cross-ecosystem, cross-region), ask "is this indicator a legitimate piece of the needed set" before asking "does this indicator alone cover everything." Before recommending a cut, check whether cutting leaves the activity with strictly less tracking than before, with nothing gained in return — if so, the cut is very likely wrong regardless of how good the stated rationale sounds.

**Also apply to recommendation precision**: don't write a specific-sounding fix ("use a different M&E indicator") without actually checking the real candidate pool (in this case `Architecture_Crosswalk` + the full M&E indicator list) for whether an alternative exists. In this session, 3 of 5 such recommendations turned out to have no real alternative at all — the honest finding was "no adequate option exists," a coverage gap, not a swap.
