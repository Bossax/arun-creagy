# 2026-08-11_dont-conflate-evidence-and-asset-in-seal-chain

**Context**: While sealing CRDB WP4 via the `/seal` skill, the first T-E-D-A chain proposal listed the gap-analysis report, the node-level deep-dives doc, and the design synthesis report as **Evidence**, and then listed the same files again as the **Assets** the seal was hardening. The user caught it in one line: "evidence and assets can't be the same." Had to redo the Evidence section entirely, replacing it with the actual raw discovered material (a live-catalog verification row, matched dataset-catalog rows, a requirement-count extraction) that grounds the deliverables, rather than the deliverables themselves.

**What worked**: Once corrected, the fix was straightforward — Evidence became the inputs/discoveries that justify a decision (things found, not things authored this session as the deliverable), and Assets stayed as the hardened outputs. The precedent was sitting right there in the ledger's own prior entries (WP2's seal used raw source documents — a donor report, a personal note, NotebookLM query outputs — as Evidence, distinct from the `WP2-Findings-Report.md` Asset it produced) but wasn't consulted closely enough before drafting the first proposal.

**Why**: The skill's own hard rules state "Motive/Artifact Separation: never log a file path in the Trigger ledger" and implicitly the same logic extends to Evidence vs. Asset — Evidence answers "what did we find that justifies this," Asset answers "what did we produce as a result." Citing a deliverable as evidence for itself is circular: it treats the existence of the work as proof the work is correct, which defeats the point of a T-E-D-A chain (grounding decisions in something external to the decision itself).

**How to apply**: Before proposing a T-E-D-A chain, check every Evidence entry against one question: "was this discovered, or was this authored as this session's output?" If it's this session's authored output, it belongs in Assets, never Evidence — even if it feels natural to list "the report we just wrote" as evidence that the work happened. Re-read an existing sealed entry in the target ledger (not just its ID/date, but its actual Evidence-vs-Asset split) immediately before drafting a new chain, rather than relying on memory of the pattern.
