# Never build a curated/compressed artifact from memory of an earlier read

**Pattern**: When producing a compressed/curated synthesis (a highlight reel, a "top 20" selection, a summary), re-read the source files fresh rather than relying on memory of an earlier full read in the same conversation. A full-detail render can survive an incomplete memory undetected — the reader still sees everything. A "pick the important subset" pass cannot: it will systematically miss whatever category wasn't salient in memory at write time, and nothing in the output signals that anything is missing.

**Concrete instance**: Building `curated-events.json` (a ~20-30 event curated timeline) for a `timeline-th` skill from memory of a `Change-Log.md` table read earlier in the conversation, instead of re-reading the full `manifest.json` (72 entries) and `Deliverable-Map.md` (~85 rows). The result silently dropped an entire evidence-gathering layer (A-BTR compliance work, interview rounds, workshops) because the implicit selection criterion — "has a matching decision row" — structurally cannot see deliverables that were sealed without ever triggering a dated decision. The user caught it by asking where specific known work streams had gone; the honest root cause was memory-based construction, not deliberate exclusion.

**Related pattern — single-string matching under-matches real document variation**: A retro-matching script keyed on one exact heading name ("Files Modified") missed a real session that used a different heading ("Verified Shipped Assets") for the same content. Same root failure as above: treating an author-chosen label, or a remembered subset of a table, as a stable schema. Prefer explicit re-reads and heading/field aliases over trusting a prior pass or a single exact match, whenever the source is freeform/human-authored rather than machine-generated.

**How to apply**: Before any compression/curation/selection step over previously-seen source material, re-read the source fresh (or delegate that re-read explicitly) rather than reasoning from what's already in context. If a fork/subagent is doing the work, its briefing should say "re-read X" explicitly, not assume the parent's memory of X is sufficient to hand off.
