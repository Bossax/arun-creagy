## AI Diary
I started with a simple documentation task and then got pulled into a very real operational failure: NotebookLM MCP looked healthy in `get_health`, but the browser context was dying on launch. My first wrong assumption was that the MCP server state itself was the main blocker. It wasn’t. The actual problem was a stale and/or locked browser profile plus auth drift, which only became obvious after I stopped looping on health checks and inspected the running browser processes. [🟧 AGENT DECISION] I initially treated “green health” as evidence that the active session was usable, which was wrong; the health payload only confirmed auth state, not session survival. Once I accepted that distinction, the recovery path became clear: kill Chrome/Edge, clean the profile, re-authenticate, and verify with a real query. That sequence restored the notebook session. The broader lesson is that MCP health is necessary but not sufficient; live session continuity is the real runtime dependency.

## Honest Feedback
The biggest friction point was the repeated collapse into `get_health` as a proxy for system health. That was misleading because auth and session lifecycle are separate concerns. A second friction point was the browser process lock behavior: multiple Chrome and Edge instances were still resident, and they likely contributed to the profile being unstable until I forcibly cleared them out. The third friction point was the re-auth UX itself; the visible and headless attempts both failed until the environment was cleaned and the browser session was re-established. This was a good reminder that browser automation reliability is as much about state hygiene as it is about timeouts and prompts.

## Lessons Learned
- A `green` MCP health state does not guarantee a live browser session.
- When `launchPersistentContext` keeps failing, inspect host browser processes before changing prompts or timeouts.
- For NotebookLM MCP, `cleanup_data(confirm=true, preserve_library=true)` is a valid recovery tool when auth drift and profile locks are suspected.
- Explicitly distinguishing auth, session, and notebook selection avoids false confidence during troubleshooting.

## Next Steps
- Keep `STEALTH_ENABLED` off for the NotebookLM MCP server when reliability matters.
- Reuse the active session while it remains live, instead of reinitializing unnecessarily.
- If the session begins failing again, repeat the browser-process cleanup before retrying auth.
