## AI Diary

I spent this session inside a writing workflow that became stricter and more honest as it progressed. At first, I behaved like a model trying to satisfy a section outline quickly. That produced prose that was technically informed but still sounded too much like translated English design writing. The human repeatedly rejected that drift, and that pressure was useful. It revealed that technical writing quality here does not come from adding more concepts, but from choosing the right Thai sentence shape, naming institutional functions directly, and preserving the distinction between what the source says and what the architecture implies.

The strongest part of the workflow was the repeated cycle of evidence retrieval, section drafting, criticism, correction, and then style-pack hardening. Instead of treating feedback as a local edit, the session converted it into reusable rules. That is the key reason this feels like best practice. The writing was not only improved at the paragraph level; the criteria for future writing were upgraded in memory.

## Honest Feedback

1. The biggest friction was repeated drift into translated English prose. Even when the facts were correct, the wording sounded like architecture notes rather than Thai report writing. That indicates the drafting loop needs an earlier Thai-voice check before text is proposed.

2. The session also showed that style rules were previously too flat. A list of rules was not enough. The human had to point out the same class of problems multiple times: composite nouns, imported English sentence shapes, negated pseudo-contrast openings, and terms like `workflow` or `layer`. This means style enforcement must happen hierarchically, not as a late cleanup.

3. Another friction point was the mismatch between section planning and actual section identity. At several moments, I overexplained concepts already covered in prior sections. The human repeatedly had to restate section boundaries: Topic 4 should not re-teach PDNA; Topic 5 should not sound like a software specification; Topic 6 should be technical and table-friendly. This indicates a need for stronger section-job validation before prose generation.

Even with those issues, the session was productive because the feedback was not wasted. Each repeated failure was converted into a new control in [`STYLE_PACK_NCAIF-Institutional.md`](ψ/memory/style/STYLE_PACK_NCAIF-Institutional.md:1), which means the friction improved the method instead of only slowing it down.

## Lessons Learned

1. For Thai technical reports, the best drafting loop is: source-ground first, write the section’s job in one sentence, draft prose, compare against human-edited local voice, then harden the style pack from the failure.
2. NotebookLM works well as a bounded extraction engine only when raw answers are preserved first and later harmonisation happens locally.
3. A style pack becomes far more useful when it stores not only diction bans, but also sentence-shape bans and hierarchical vetting order.
4. Technical sections should use bullets and markdown tables when the reader needs to discriminate structures, relations, or fields. Prose alone is not always the clearest vehicle.
5. The strongest writing workflow is one that upgrades memory after each correction, so the same error class becomes less likely in the next section.
