previous one. Boss didn't accept my first cost-efficiency plan at face value —
they made me check it against my own retro's stated friction points, which
forced me to admit two things I'd have preferred to leave implicit: the plan
doesn't restore quota visibility, and it doesn't actually force a pre-batch

The more interesting turn was being asked "doesn't the skill specify the

always, for both platforms. Neither session was "the skill working as

## Honest Feedback

Three friction points, stated plainly.

First, the blind forward test — the one verification step the plan calls
"required by the skill's own maintenance rule for a behaviorally significant
revision" — is not done. I ran the mechanical checks (drift sync, 44/44 unit
tests) because they're cheap and immediate, and deferred the one check that
actually exercises the new fork path against a real Stage 5 review, because it
requires a live section run. That's the correct call given session boundaries,
but it means this upgrade is unverified in the one way that matters most: I
don't yet know whether a forked Stage 1/3 call actually produces the same
quality of argument map and prose as a fresh one, only that it's architecturally
sound on paper.

Second, I wrote a fairly large surface of new spec text — a new SKILL.md
subsection, a rewritten invocation block, two new schema fields — in a single
plan-mode pass without an intermediate check-in on the drafted prose itself
before implementing. The three `AskUserQuestion` decisions covered the shape of
the change; they didn't cover whether the actual wording holds up. If any of
it reads awkwardly to a future subagent trying to follow it (the mapper/
verbalizer/reviewer prompts are literally instructions another model will
execute), that won't surface until the blind forward test, not before.

Third — smaller, but worth naming — this session's own token cost was not
tracked against the very quota-burn problem it was fixing. I don't know whether
this session, on its own, was cheap or expensive relative to the account's
5-hour window, because (as documented in the fix itself) there's still no way
to check that from inside a session. Slightly uncomfortable to write a
cost-efficiency upgrade without being able to measure whether writing it was
itself efficient.

## Lessons Learned

1. **A cross-agent behavior difference is often a spec gap wearing a costume.**
   The instinct to explain "why do these two agents behave differently" as an
   agent-capability question was wrong. Reading the actual invocation spec
   showed both agents were interpreting (or ignoring) the same underspecified
   rule. The right diagnostic question is "what does the spec actually say,"
   not "what did each agent choose to do" — the latter only tells you about
   deviations, not about the shared root cause.
2. **A retro's recommendations should survive being checked against its own
   findings.** Asking "does this plan solve what the retro described" is a
   cheap, high-value audit step, and it's one I should apply to my own plans
   proactively rather than waiting to be asked.
3. **Don't spawn research agents to research your own recent context.** For a
   plan-mode task whose scope was already fully established in-conversation,
   direct `Read` calls on the five known target files were strictly better than
   Explore agents — cheaper, more precise, and consistent with the actual
   content of the plan being written.
4. **A structural fix (spec correction) generalizes better than a tactical one
   (agent-specific tuning).** Framing this as "fix `subagent-prompts.md`'s
   invocation spec" rather than "make Claude Code smarter about forking" means
   the fix is legible to whichever agent reads the skill next, not just
   memorized behavior for this session.
