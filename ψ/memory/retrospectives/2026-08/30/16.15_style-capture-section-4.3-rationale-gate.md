The other correction — on the roles-paragraph reframe — was subtler and more interesting: I'd pattern-matched to the pack's own "Passive/Defeatist Syntax Elimination" category, which felt like a good, confident match, and it was *almost* right but not quite the actual mechanism Boss was pointing at (restating an obvious premise vs. defeatist framing specifically). I'm satisfied I logged the corrected, narrower version in the capture-history file rather than either forcing my original hypothesis through or just dropping the pattern.

## Honest Feedback

**Friction 1 — Question volume.** Two batches of four `AskUserQuestion` calls in one style-capture pass is a lot of interruption for one file's diff, even though the skill mandates the rationale gate for good reason (the 2026-08-30 incident it cites — three patterns promoted on inference alone, one of them wrong — is exactly the failure mode I'd have repeated on the version-tag question if I hadn't asked). I don't think the volume was avoidable given the skill's design, but it's worth watching whether future §4.4/§4.5 captures produce the same load; if so, that's a signal the skill should batch more aggressively or triage low-stakes candidates differently rather than asking about all eight.

**Friction 2 — Stale pulse data.** Both `/recap` and `/rrr` are instructed to read `ψ/data/pulse/*.json` and weave momentum into the narrative, but the files have been frozen since March 2026 (1 session, 0 messages today, despite an obviously active project). I skipped the weave-in both times rather than fabricate a "day N of an unbroken streak" line that would be false. This isn't costing anything functionally, but it means two skills are carrying instructions for a data source that's silently broken — worth fixing the pulse heartbeat mechanism itself at some point rather than continuing to work around it session after session.

**Friction 3 — Self-checking before asking.** The one real process gap this session (not checking existing rules before drafting a rationale-gate question) is the kind of mistake that's cheap to make and easy to miss, because "ask the user" always feels safe. But asking about something already decided isn't neutral — it costs Boss's attention and, cumulatively, trust that the pack is actually being read rather than treated as a index I query only when convenient. I've written this up as a feedback memory; the real test is whether the next style-capture run actually shows the check happening before the question, not just whether the memory exists.

## Lessons Learned

- **Check the pack for a matching principle before asking about a "new" candidate** — an edit that looks novel may just be an instance of a rule already on the books, scoped narrower than it should be. See `feedback_check_existing_rules_before_treating_edit_as_novel.md`.
- **Reading an explicit in-line annotation (Boss's `%%...%%` comments) counts as knowing the rationale** — don't spend an `AskUserQuestion` re-asking something already stated in writing in the diff itself.
- **A rationale-gate answer can correct the hypothesis, not just pick between two pre-built options** — when that happens, log the corrected framing in the capture-history file, not the original guess, so the next capture round inherits the right pattern.
- Pulse data (`ψ/data/pulse/`) is stale and should not be treated as ground truth by `/recap` or `/rrr` until its update mechanism is fixed.
