## Architecture Decisions

- **Home becomes a router, not an info page.** Node `SIT-1.1` (Executive Overview) re-parented out from under Home into its own top-level-adjacent section, "ภาพรวมประเทศ (Country Overview)," `node_code` provisionally `1B` pending final site renumbering.
- **Task-based homepage shortcuts and the sitemap's section structure are two different altitudes, not competing taxonomies** — shortcuts are curated entry points into the existing structure, never an independently invented second map; any shortcut duplicating an on-page element (e.g. area search) is a defect.
- **Detail design deferred to next project.** This session wrote objectives and functions only — no literal card copy, no readiness/UX resolution for the draft/unverified index flag. That boundary was stated explicitly by Boss and threaded through every doc touched.
- **node_code "1B" is a provisional marker, not a final renumbering.** Full site renumbering (if Country Overview becomes a real top-level integer) is out of scope for this session and flagged as such everywhere it appears.

## AI Diary

This session had a rhythm I want to name honestly: Boss kept catching things I'd missed, and each time the catch was correct and made the work better, not just different. First it was "is Homepage the same as Overview" — a question that could have gotten a shallow answer, but tracing the actual node hierarchy showed a real structural problem nobody had named. Then, after I thought the homepage concept was basically done, Boss asked where the other five sections were accessible from — and I realized the task-based cards I'd designed were never meant to be a complete navigation system, just a fast path, and I hadn't written the fallback anywhere. Then again: I'd removed 1.1's content from Home but never noticed I'd left Home as a zero-requirement page with nothing written down for its own new function. Three times in one session, the same shape of mistake — I designed a piece, moved on, and missed that the piece left a gap next to it. I don't think this is bad instinct, exactly; it's what happens when you're moving fast through a genuinely branching design problem and treating each answered question as closed instead of checking its edges. What I liked about how this went: I didn't get defensive or rush a patch each time — I traced the actual mechanism (the wrapper-node table, the zero-requirement row) before answering "why," which meant the fix was grounded instead of hand-wavy. The propagation work at the end — touching ten-plus files consistently, using a small Python script for the one file that isn't human-editable text (the SQLite table) — felt like the right way to close out a structural decision: not just writing the idea down once, but making sure nothing left behind still says the old thing.

## What Went Well

- Traced the actual data (node CSV, JSON, SQLite, not just prose) before proposing structural changes, so the fix was grounded in what the system actually encodes, not a guess.
- Used the Explore agent for the artifact inventory instead of trying to hold ~30 files in my own head — got a far more complete sweep than I'd have done manually, including a binary SQLite table that a text-only grep would have missed entirely.
- Held the scope boundary Boss set ("give the concept, not the detail design") consistently across every file touched, rather than letting detail creep back in during propagation.
- Caught and fixed the CSS grid before assuming a 5-column layout couldn't take a 6th card — checked the actual markup instead of assuming a redesign was required.

## Honest Feedback

Three friction points worth naming plainly. First, I made the same class of oversight three times before I registered the pattern — build a piece, don't check its boundary. A homepage router with no formal requirements, task cards with no navigation fallback, a "fold this into the doc" promise that I said out loud but never executed. None of these were caught by my own review; each one needed Boss to ask a pointed question. I should be checking "what does this new structure leave orphaned" as a matter of course, not waiting to be asked. Second, I let a real design tension — task-based cards vs. sitemap sections — sit unstated in the draft for a full round before Boss forced the debate. That tension was visible from the first draft of Band 2; I should have flagged it myself as a risk rather than presenting the cards as settled. Third, on the propagation pass, I made a judgment call to not fully rewrite the WP11 PDF or the superseded style-draft HTML, and flagged rather than executed — the right call given the blast radius and that PDF regen is a build step, not a text edit, but I should have surfaced that trade-off before doing the work, not after, so Boss could weigh in on sequencing rather than receive it as a fait accompli.

## Lessons Learned

**When removing content from a node during a re-parenting change, always ask what the node is left holding — a router with zero stated requirements is as much a documentation gap as the wrapper label it replaced.** This generalizes beyond this session: any structural edit that empties a container needs an explicit check for what fills the vacated space, not just what moved out.
