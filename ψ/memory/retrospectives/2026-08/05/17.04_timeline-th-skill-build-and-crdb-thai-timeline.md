## AI Diary

This session had a real rhythm to it: design, build, ship, then get corrected — repeatedly — and each correction taught me something I should have caught myself. The pattern that stings most in hindsight is the curated-events.json content gap. I built it from memory of a `Change-Log.md` I'd read earlier in the conversation instead of re-reading the actual source files, and it silently dropped an entire evidence layer (A-BTR, all the interviews, the workshops) because my selection criterion was implicitly "has a matching decision row" — which structurally can't see evidence-gathering work that never triggered a dated decision. When the user asked "where is the A-BTR incorporation? where are the workshops and interviews?" I had to admit the honest answer was my own shortcut, not a deliberate exclusion. I fixed it by forking a proper re-derivation with explicit criteria, but the real lesson is upstream of that: I should have distrusted my own memory of a 35-row table the moment I was about to build a curated artifact from it, not after being asked pointed questions. The next-steps sourcing had a similar shape — I grabbed "the most recent retro" mechanically without checking whether that session was actually about the project or about internal housekeeping, and later discovered (while investigating the user's follow-up correction) that an even more recent, genuinely relevant retro existed but was invisible to my own matching script because it used a different heading name than the one I'd hardcoded. Both bugs share a root cause: treating "I did something" as equivalent to "I verified it was right," when the actual fix each time required going back to primary sources instead of trusting my own prior pass.

## Honest Feedback

Three friction points worth naming plainly. First, the environment itself introduced real risk to this session's core safety property (read-only against the ledgers) — twice the IDE silently reformatted `CRDB-Change-Log.md` just from having it open in a tab, and I only caught it because I'd built the habit of running `git status` on the protected paths after every script run. If I hadn't been checking that reflexively, a ledger the whole `/seal` system depends on could have drifted without anyone noticing until much later. That's not my bug to fix, but it's worth surfacing loudly: the user's editor auto-formatting open files is an active hazard for a workflow whose entire premise is "never touch these four files." Second, I fell into scope drift on the HTML design step — I built a full mockup with mockup content before confirming the underlying data-to-template mapping was even designed, which meant real integration work (the curated-events.json schema, the selection criteria) got backfilled after the visual design was already locked in, rather than the reverse. It worked out, but design-then-plumbing is riskier than plumbing-then-design when the plumbing is where the actual judgment calls live. Third, I used forks for genuinely large generation tasks (72-entry translation, 27-event re-derivation) which was the right call for keeping my own context light, but the first fork attempt had to be aborted mid-flight because I gave it an instruction set that still had the old "cache Thai in manifest.json" design in it — I hadn't fully propagated an architecture correction from earlier in the conversation into the fork's briefing before launching it. Forking compounds a stale-instruction bug because the fork can't be quietly corrected the way I can correct myself; it has to be caught and redirected via message, which costs real time.

## Lessons Learned

1. **Never build a curated/compressed artifact from memory of an earlier read — re-read the source.** Compression amplifies the cost of an incomplete memory: a full-detail render might survive an incomplete memory undetected, but a "pick the important 20%" pass will systematically miss whatever category wasn't salient in memory, and won't self-correct.
2. **A matching/selection heuristic keyed on one exact string (a heading name, a field name) will silently under-match real variation in freeform documents.** Both the "Files Modified" heading and the memory-based `CH-` row selection failed the same way: treating an author-chosen label as if it were a stable schema. Prefer aliases/fallbacks over a single exact match whenever the source documents aren't machine-generated.
3. **Before launching a fork with a large briefing, re-read the fork prompt once against the most recent correction in the conversation, not just against the original plan.** An architecture correction made 10 messages ago is easy to leave out of a freshly-written fork prompt if you're drafting from the plan document rather than from the live state of the conversation.
