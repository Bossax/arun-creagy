## AI Diary

This session had two genuinely humbling moments and I want to be honest about both. The first was misdiagnosing the source markdown's changed content as a Read-tool hallucination — I built a whole "the tool fabricated text" narrative and said so to the user before actually checking `git diff`, which showed it was just an uncommitted edit the user had made themselves. The instinct to distrust the tool wasn't crazy (there's a real precedent in this project's memory of Grep mangling Thai text), but I reached for the more dramatic explanation before the boring one, and I told the user the dramatic version out loud before verifying it. That's backwards — verify first, narrate second.

The second was building the entire first version of `index.html` from a *summary* of the design preset (`STYLE_PRESETS.md`'s prose description) when the user had a full working reference implementation sitting in a sibling directory the whole time. I only found `creagy_template_example.html` because the user pointed me back at the preset file and I happened to notice a `Visual reference` line had appeared in it. In hindsight, "read the reference implementation before inventing my own CSS system" should have been the very first move, not a mid-build correction.

What actually went well: once I had the real reference file, I resisted the urge to just wholesale-copy it and instead extracted the concrete facts (colors, class names, structural patterns) and asked what depth of fidelity the user wanted before assuming pixel-perfection was the goal. And the content-accuracy passes near the end — the Rent_Housing framing, the broken GIS sentence, the roadmap restructure — felt like real editorial collaboration rather than me just executing instructions; I pushed back with reasoning on the "innovation" framing rather than silently complying, and the user engaged with that reasoning rather than just overriding it.

## Honest Feedback

Three friction points, stated plainly. First: I should default to searching for an existing reference/template *before* building CSS from scratch when the user's context is this clearly an established brand system (Creagy Corporate) — the PPTX inspection I did before Phase 3 wasn't wasted, but it should have prompted me to ask "is there already a working HTML version of this?" rather than assuming I needed to derive everything from a PowerPoint. Second: I never got a working automated visual-overflow check for the final version of the deck. The claude-in-chrome extension connected once, early, then disconnected and never came back for the rest of the session — I fell back to just opening the file in the default OS browser, which means several rounds of structural edits (adding 17 intro paragraphs to already-dense slides) shipped without me actually confirming no overflow occurred, only my own text-length estimate. That's a real gap the user should know about before treating this deck as presentation-ready. Third: the file was being edited by both of us concurrently at least twice, and I only detected that via content mismatches rather than any proactive check — I should have run a quick `git diff`/mtime check before *every* edit in a session like this, not just after being confused by unexpected content, given this project's established pattern of the user editing files directly mid-session.

## Lessons Learned

- **Before Building From a Style Preset, Search For a Reference Implementation** — When a style preset (`STYLE_PRESETS.md`) has both a compact prose description AND potentially points to a real file, always check for and read the real file first; a prose summary is lossy compared to an actual working template with real class names, spacing, and structure. See `[[frontend-slides-preset-vs-reference-implementation]]`.
- **Verify File State Via Git Diff Before Diagnosing a Tool as Hallucinating** — When a Read result doesn't match expectations, the boring explanation (file changed on disk since last read, possibly by the user directly) should be checked via `git diff`/`git status` *before* the dramatic explanation (the tool fabricated content) is voiced to the user.
- **Structural Fixes to a Long Generated Document Need Visual Re-Verification, Not Just Text-Length Estimation** — Adding content (like 17 one-sentence intro paragraphs) to an already-dense fixed-canvas layout is exactly the kind of change that needs a real rendered screenshot check, not a "this is probably short enough" judgment call, especially when overflow is silent (no error, just visually broken).
