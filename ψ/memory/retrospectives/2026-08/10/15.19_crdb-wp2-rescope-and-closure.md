## Architecture / Process Decisions

- **A false "corruption" finding propagated through a full Stage B run before being caught** — the background diff subagent's claim of ~55,700 corrupted Thai characters was accepted and built into a whole v3-fallback-join mechanism, and only unraveled when Boss asked "why were the Thai texts corrupted, what decoder did you use" — a question that assumed the premise was worth re-checking. Direct byte-level inspection (`xxd`/`od`, counting literal `0x3F` bytes) immediately falsified it: zero corruption, the earlier subagent's "confirmed via raw byte inspection" claim was itself false. The actual cause was the `Grep` tool's content-display path silently mangling multi-byte Thai UTF-8 on this Windows/Git-Bash environment, while `Read` and raw `xxd`/`od` rendered it correctly.
- **Scope correctness turned out to matter more than analytical depth** — the first Stage B pass (all 8 services, full catalog, top-10 shortlist) was methodologically sound *and* still wrong, because it re-derived a scope Boss had already explicitly rejected one day earlier in the sprint plan's own change history. Tracing that history (rather than trusting the task framing baked into the Stage A document's own purpose statement) was what surfaced the mismatch.
- **Comment-incorporation via direct Edit-tool paste is unreliable with Thai text** — a copy-paste of a Read-tool excerpt containing Thai script silently corrupted characters mid-transcription once (turning "overlaps" into "overลาป" mid-word) when passed back into an Edit `old_string`. Switched to Python-script-based exact-string replacement (write the replacement logic to a heredoc, run via Bash) for every subsequent Thai-bearing edit, which never had this failure mode.
- **NotebookLM's "no substitution on failure" rule held under real pressure** — a rephrased query genuinely timed out after 3 minutes, and the correct move (per the `notebooklm-rules` skill) was to report the failure and stop, not fall back to general knowledge or a different source. This was tested for real, not hypothetically.
- **Track 3 deferral was the right instinct, later vindicated** — Boss's decision to defer the DCCE-risk-map-inputs track "for later" meant the session's compute went entirely into two tracks that could actually be finished and sealed this session, rather than spreading across three and finishing none cleanly.

## Honest Feedback

Three friction points worth naming plainly. First, the subagent-corruption-claim failure was avoidable at essentially zero cost — a single `xxd` spot-check before accepting "confirmed via raw byte inspection" as true would have caught it immediately, and I should treat strong-sounding verification language from a subagent as a claim to spot-check, not a fact to build on, especially before launching another expensive agent run downstream of it. Second, the Edit-tool Thai-text corruption bug (copy-pasting a Read excerpt containing Thai script into an Edit call, and having characters silently mangle mid-paste) is a real and somewhat scary failure mode because it's *silent* — nothing errored, the edit just failed to match on the first attempt due to corrupted old_string, which was the only reason it was caught. If the corrupted string had happened to still match something in the file, this could have written wrong content without any error surfacing. I don't have full confidence this is fully resolved by "use Python scripts instead" — it's a workaround for this session's specific instances, not a diagnosed root cause. Third, the session ran long (~5.5 hours, single continuous thread) with several points where a mid-session `/rrr` might have captured the corruption-discovery lesson closer to when it happened, with fresher detail — by the time this retro is being written, the exact sequence of the "why is v4 corrupted" investigation is being reconstructed from conversation history rather than fresh memory, which is a real (if minor) cost of long uninterrupted sessions on this kind of skill.

## Lessons Learned

**A subagent's "confirmed via [verification method]" claim is a claim, not a fact — spot-check it directly before building expensive downstream work on top of it, especially when the claim is surprising.** The corruption report used strong, specific verification language ("raw byte inspection... not a rendering issue") and was still completely wrong. The cost of a direct spot-check (one `xxd` call) is trivial compared to the cost of an agent-run built on the wrong premise.

**When a task's own framing document states a goal ("identify the top 10 most business-critical datasets"), check whether that goal has since been superseded by a later project decision before treating it as current scope** — the Stage A document's purpose line was accurate when written, but a scope-narrowing decision the next day made it stale, and nothing about the document itself signaled that. The check that caught this was tracing the sprint plan's own change-log, not re-reading the task document more carefully.
