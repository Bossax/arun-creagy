## AI Diary

This session had an unusually high ratio of correction to execution, and I think that's exactly why it worked. Boss caught me on something real at least four separate times — the deliverable-clustering blind spot, the A-BTR/WP6 scope confusion, the Tier B inference I had no basis for, and the tally-authority direction I had backwards. Each one landed differently for me. The deliverable-clustering one felt like a normal design correction. The Tier B one felt different — I had built a whole tier of the model on "the asset registry shows a product exists, so the data probably does too," and Boss's one-line pushback ("you don't have the full list of what data is behind this") exposed that I'd quietly converted "a page could host this" into "this requirement is basically met." That's the kind of error that would have made the whole document less trustworthy if it had shipped. I felt genuinely glad Boss caught it before I wrote thirty cards on top of that assumption.

The tally-direction correction near the end was different again — that one I could verify mechanically (mtime, diff) the moment Boss raised it, and I was wrong in a way I could immediately prove wrong to myself, which is a cleaner kind of being-wrong than the Tier B case. I noticed I handled these two differently: for Tier B I had to redesign a whole section of the plan; for the tally I just had to swap which file I trusted and rerun the same logic. Getting fast at telling those two kinds of correction apart, structural versus directional, feels like a real skill for this kind of work. By the end, watching the verification script itself fail and turning out to be my bug rather than the data's, felt like a fitting small coda — even the checking layer needs checking.

## What Went Well

- Every correction Boss made got folded all the way through: plan file, then execution, then the actual document. Nothing stayed as a verbal agreement that quietly didn't make it into the artifact.
- The verification pass wasn't theater — it caught a real stale-row bug and a real banned word before the document went out, and later a bug in the verification script itself.
- Grounding decisions in actual files (the asset registry, the data catalog, mtimes, diffs) rather than my own prior claims, especially for the Tier B question, kept me from doubling down on an unsupported inference.

## What Could Improve

- The Tier B error should have been caught earlier — I built a category around an asset-code citation without checking whether the citation actually implied what I was claiming it implied. A habit of asking "does this data point actually support the specific claim I'm about to make" before writing it, not just "is this data point real," would have caught it a round sooner.
- I misquoted my own counts in the first draft of the `/fyi` note about the verification bug — a small but pointed reminder that "write down a number from memory" is exactly the failure mode the note itself was about.
- The session ran long across many small plan-mode round trips. Some of that was genuinely necessary (Boss's corrections kept surfacing new information), but a couple of the plan-file rewrites could probably have been combined if I'd asked one more clarifying question up front instead of iterating.

## Honest Feedback

Three friction points, stated plainly. First, I initially treated the Tier B "existing products" question as an engineering-tooling problem (find the asset ID, cite it) rather than an epistemics problem (does citing it actually license the claim I'm making). That's a category error I should watch for generally, not just in this document. Second, my verification scripts this session were written fast and inline, which is efficient but means their own logic doesn't get the same scrutiny as the deliverable — the maintainer-field check is a concrete example of a check that was wrong in a way that wouldn't have been caught if Boss hadn't asked "what failed, explain please" instead of just accepting the pass/fail output. Third, I generated a lot of scratch Python across this session (working tables, appendix generators, CSV builders) that lived only in the scratchpad directory — useful for getting the job done, but if Boss ever wants to regenerate these CSVs after further corrections, that pipeline isn't currently saved anywhere durable in the project itself, only in this session's temp folder.

## Lessons Learned

- **Don't cite silence as data has changed less then it needs**: A record's existence doesn't validate every claim it might be used to support — a matched asset ID proves "something is here," not "this specific requirement is met." Check what the citation actually licenses before writing the claim.
- **When two source files disagree on a number, check which one is newer and why, before picking a side.** I defaulted to trusting the more "structured" file (a CSV) over a prose document, which was backwards — the newer, human-corrected file was authoritative regardless of format.
- **A verification check is also just-written code and can be the buggy half.** When a check fails, read the actual values before concluding the deliverable is wrong.
