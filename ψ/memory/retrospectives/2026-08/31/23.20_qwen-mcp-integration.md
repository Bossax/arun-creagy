## AI Diary

This one had a good rhythm to it — Boss kept steering in small increments ("just make a tool, why mcp", then reversing to "plan to implement mcp") and I adjusted without much friction, which felt right rather than defensive. The part I'm most satisfied with is refusing to guess twice: when `mcp[cli]` turned out to be a major-version bump with a renamed class, I introspected the installed package instead of pattern-matching from training-data memory of the old API, and when the model roster didn't match what Boss asked for (`qwen-max` doesn't exist on this account), I surfaced the live discrepancy and asked rather than silently substituting something close. Both of those were places where an older habit — confidently emitting plausible-looking code — would have produced something that either crashed on import or silently used the wrong model without Boss noticing.

The env-var failure at the very end is the interesting one to sit with. My selftests were genuinely green — I ran real API calls and got real "pong" responses — but the actual integration was still broken for the reason that mattered: the MCP-spawned subprocess doesn't see what my manual PowerShell command sees. I didn't fabricate success, but I also didn't think to ask "does my test process inherit environment the same way Claude Code's MCP launcher will" until it broke for real. Worth internalizing: a passing selftest that manually patches the environment isn't proof the deployed path works — it's proof the code works given the environment. Those are different claims.

## Lessons Learned

- A selftest that manually injects an environment variable does not validate the deployed launch path if the real launcher (Claude Code's MCP subprocess spawn) inherits environment differently. Test the actual invocation shape, not a patched stand-in for it — see `[[feedback_no_audit_tone_in_deliverables]]`-adjacent instinct: verify claims against the real mechanism, not a convenient proxy.
- Windows User-scope env vars set via `SetEnvironmentVariable`/`setx` don't propagate to already-running login sessions — only new logons pick them up. Any tool relying on such a var (this MCP server, or future ones) should either read the registry directly as a fallback or the setup instructions should say "sign out and back in," not just "set the env var."
- When a task involves an external API roster that the model itself can enumerate (`qwen_list_models`), run that enumeration *before* asking the user to name specific model IDs from memory — model names drift and get retired; ground truth beats recollection for both the model and the human.
- MCP SDK major-version bumps (mcp 1.x → 2.x) silently rename core classes (`FastMCP` → `MCPServer`) — pin the major version in dependency specs for a script meant to be reproducible via `uv run`'s inline deps, and when an import fails, introspect the installed package rather than guessing at the new shape from memory.
