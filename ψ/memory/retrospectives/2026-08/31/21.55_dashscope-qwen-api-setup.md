## Lessons Learned

- **Git Bash on Windows mangles UTF-8 in inline `curl -d '...'` shell arguments.** Non-ASCII payloads (Thai text tested here) must be written to a file first and sent via `--data-binary @file.json`, with `Content-Type: application/json; charset=utf-8`. Inline `-d` silently corrupts the encoding rather than erroring, so a 200 response with garbled/wrong-language output is the only symptom — always inspect the actual response body, not just HTTP status, when testing non-ASCII API calls from this shell.
- **DashScope private MaaS gateway endpoints don't follow the public docs' `/api/v1/chat/completions` path.** For this workspace's gateway (`ws-pg8s7yunzcnexczp.ap-southeast-1.maas.aliyuncs.com`), the working paths are `/compatible-mode/v1/chat/completions` (OpenAI-compatible) and `/api/v1/services/aigc/text-generation/generation` (native DashScope format). A bare `/api/v1/chat/completions` 404s.
- **Windows user env vars set via PowerShell `SetEnvironmentVariable` don't propagate to an already-running shell session** (including a Bash tool call in the same Claude Code session) — they only appear in newly spawned processes/terminals. For same-session testing, export the value directly into that one shell call rather than relying on the persisted var.
