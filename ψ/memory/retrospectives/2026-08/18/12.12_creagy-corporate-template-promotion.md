## Honest Feedback

Three friction points worth naming plainly. First, I was slow to escalate from "reason about the code" to "look at the actual render" — I had browser automation tools available the whole time and didn't reach for them until directly told my assumptions were wrong, twice. That's a real gap: when a user reports something is visually broken after I've made a change, checking the actual rendered output should be close to automatic, not a last resort after repeated denial. Second, I introduced a genuinely bad design pattern (low-opacity "ghost numeral" filler text) to solve a legitimate problem (empty cell space) and then had to walk it back after it kept getting reported as a bug — a case where the "clever" solution (borrowed from a template pack's stated philosophy) didn't survive contact with actual readability testing at real scale. Third, and structurally the most important: the same CSS cascade bug (single-class override losing to a later same-specificity rule) bit three different components before I stopped and asked "is this a pattern, not an instance" — I should have generalized after the second occurrence, not the third, and the fix that stuck was writing the anti-pattern into permanent documentation rather than trusting memory to catch it next time.

## Lessons Learned

- **When a user reports "nothing changed" or "still broken" after a fix, verify against the actual rendered output before re-reasoning about source code** — a second denial should trigger direct inspection (browser tools, screenshots, computed styles), not another round of static analysis.
- **A recurring bug class (same symptom, different location) is a signal to write a rule, not patch another instance.** The CSS cascade bug (bare single-class overrides losing to later same-specificity declarations) recurred three times before being generalized into a documented "always use compound selectors" rule.
- **Never fade bare colored text against its own background for visual sequencing — only fade filled/bounded shapes** (badges, bar-fills). This was independently rediscovered twice in one session before being written down.
- **Decorative filler that looks like unreadable text will be reported as a bug regardless of design intent** — low-opacity "ghost" typography used purely to occupy empty space is a rejected pattern now, in favor of adding real content.
- **Size-as-emphasis must never conflict with reading order** — a bigger/featured item in a numbered sequence must stay in its numeric position (win via width/color), not move to a visually-first grid cell.
- **Fixed-stage (1920×1080, scale-to-fit) decks must be sized for realistic windowed viewing (~0.6-0.8x scale), not full-viewport width** — font sizes that look right in a full-width screenshot will read as too small in normal use.
