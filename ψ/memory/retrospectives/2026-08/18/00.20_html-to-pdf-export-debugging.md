## Timeline

- Exported HTML→PDF via `chrome --headless --print-to-pdf`, using the deck's existing `@media print` CSS (A4 landscape + `zoom: 0.585`, inherited verbatim from the WP9 canonical template). Reported success based on page count and file size alone — no visual check.
- Boss: "no the pdf is inccorectly foramat." No further detail given.
- Tried to inspect the PDF directly with the `Read` tool's PDF page-rendering — failed, `pdftoppm`/poppler not installed in this environment.
- Tried `claude-in-chrome` browser tools to screenshot the PDF — extension not connected, dead end.
- Fell back to Python: installed `pymupdf` via pip, rendered PDF pages to PNG, and used the `Read` tool on those PNGs to actually see the output.
- **Bug 1 found**: content occupied only the top-left ~60% of the page, blank elsewhere. Root cause: Chrome's headless `--print-to-pdf` does not reliably honor CSS `zoom` during PDF generation, so the `zoom: 0.585` scaling hack (tuned for a different print pipeline, e.g. the interactive browser print dialog) produced an unpredictable partial scale instead of filling the A4 page.
- Fix: replaced `@page { size: A4 landscape }` + `zoom: 0.585` with `@page { size: 1920px 1080px }` and no zoom at all — matches the slide's native pixel dimensions 1:1, removing all DPI/zoom guesswork.
- Re-rendered page 1 — fixed. But re-checking page 2 (Table of Contents) showed a **second bug**: totally blank body.
- **Bug 2 found**: the deck's on-screen "reveal" animation (`.reveal { opacity:0 }`, flipped to `opacity:1` only via a `.slide.visible .reveal` selector that JS applies to whichever slide is currently on screen) meant every slide except the one active at print time rendered with invisible content. The existing print CSS forced the `.slide` container itself visible but never touched the nested `.reveal` children.
- Fix: added `.reveal { opacity: 1 !important; transform: none !important; }` inside `@media print`.
- Re-checked all pages by rendering thumbnails — most fixed, but the CDM 8-domain table slide (slide 12) still showed only 5 of 8 rows, with a large blank gap before the footer, and the header's first column text was invisible.
- Investigated via PDF text extraction (`page.get_text('dict')`, sorted by y-coordinate) rather than continuing to eyeball screenshots — confirmed rows 6–8 were **completely absent** from the extracted text layer, not just visually clipped. Ruled out an overflow/height-clipping theory (there was plenty of blank space below the visible rows, which wouldn't happen if simple clipping were the cause).
- **Bug 3 found (two bugs actually)**: (a) a Chromium print-pagination quirk with `<table>` elements that silently drops rows instead of paginating or erroring — a known fragile pattern; (b) a genuine pre-existing CSS bug inherited from the WP9 canonical template: `table.data-table td:first-child, table.data-table th:first-child { color: var(--creagy-dark-navy) }` accidentally recolored the header's first cell text to match its own dark-navy background, making it invisible regardless of the table-print bug.
- Fix: converted the CDM slide from a `<table>` to the same `grid-4` card layout already proven reliable elsewhere in the deck (sidesteps the Chromium table bug entirely), and separately fixed the CSS selector to `td:first-child` only so any future `data-table` usage across the other WP11 decks won't inherit the same invisible-header bug.
- Verified the final fix properly: extracted text from all 21 pages and confirmed plausible, consistent character counts on every page (not just a visual spot-check), plus visual confirmation of cover, TOC, the converted card slide, and a sample of grid layouts.

## AI Diary

Boss's one-line "no the pdf is incorrectly format" carried no diagnostic detail, and my first instinct was to try to *see* the PDF directly, which turned into its own mini-struggle: no poppler, no working browser extension, and I had to improvise with a pip-installed PyMuPDF just to get eyes on the actual output. That felt like a environment-tooling gap worth remembering for next time rather than something to route around silently.

What I'm most glad about is that I didn't stop at the first fix. The zoom/page-size bug was the obvious, visually loud one, but if I'd declared victory there I would have shipped a deck with a blank TOC and half the CDM slide missing — bugs that are much easier to miss because they don't scream "broken" the same way a shrunk-into-a-corner slide does. Switching from "look at a screenshot and eyeball it" to "extract the actual text layer and check for missing content programmatically" was the turning point for the third bug — screenshots at low resolution genuinely couldn't tell me confidently whether 5 rows or 8 rows were present until I went to the text layer directly. I think the discipline of re-verifying *every* page after each fix, rather than just the one page I knew was broken, is what caught bug 3 in the first place — bug 2's fix looked complete after checking 3-4 slides, and bug 3 was hiding in slide 12 specifically, which I would not have checked without doing a full sweep.

## Honest Feedback

Three friction points worth naming. First, my initial "export succeeded" claim was too confident given the verification I'd actually done (page count + file size, nothing about content legibility) — I should default to at least one visual spot-check before reporting any export/render task as complete, especially for anything involving CSS print behavviour, which is notoriously inconsistent across engines. Second, the environment gap around PDF inspection (no poppler, no connected browser extension) cost real turns before I found a working path via PyMuPDF; if this comes up again, going straight to "pip install pymupdf and render to PNG" would save time versus trying the Read tool and browser tools first. Third, and most interesting: two of the three bugs (the zoom/print mismatch, and the table-pagination-drops-rows Chromium quirk) are print-CSS pitfalls specific to headless `--print-to-pdf`, not things that would show up if someone just eyeballed the HTML in a normal browser tab. That's a category of bug that's genuinely easy to ship silently, and it's why the "just check page count" verification felt reasonable in the moment but wasn't enough.

## Lessons Learned

- Chrome's headless `--print-to-pdf` does not reliably apply CSS `zoom` — for pixel-perfect slide-deck-to-PDF export, size `@page` to match the content's native pixel dimensions exactly and skip zoom-based scaling entirely, rather than trying to fit content onto a physical paper size via a scale hack.
- JS-driven "reveal on active slide" animations (common in slide-deck HTML templates) need an explicit print-mode override forcing all `.reveal` elements permanently visible — otherwise only the one slide that happened to be active gets printed with content, and every other slide silently prints blank.
- `<table>` elements are a known-fragile pattern under headless Chrome print pagination — they can silently drop rows without erroring, without inserting a page break, and without any signal other than the missing content itself. Prefer grid-of-cards layouts (already proven elsewhere in a deck) over `<table>` for anything that will be print-exported.
- When verifying multi-page generated output, don't stop at the first bug found even if it looks like "the" bug — do a full page-by-page sweep after every fix. A fix that looks complete after spot-checking 3-4 pages can still leave a different bug hiding on a page you didn't check.
- For diagnosing "is this content actually there," extracting the underlying text layer with y-coordinates is more reliable than eyeballing screenshots, especially at the compressed resolutions convenient for quick visual checks.
