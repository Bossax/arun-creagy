## Lessons Learned

- When a user says "use trace or oracle_search if needed," treat oracle_search as the fast first pass and the /trace skill as the escalation — but the skill's "5 parallel subagents" default should be treated as one *option* the skill offers, not a mandatory step, when a targeted Grep across a known local directory tree can answer the same question faster and just as reliably. Document the substitution when it happens.
- For project-specific "collaborative session guide" documents that walk through discrete question groups (A, B, C...), the established rhythm (discuss → draft → user confirms → write to both files → mark resolved) survives context compaction cleanly as long as the summary preserves the *pattern name*, not just the content — worth explicitly naming these workflow patterns in future summaries so they're easy to resume.
- Grounding an "I don't know, it depends" answer in the project's own prior work product (rather than either inventing a plausible-sounding framework or leaving it vague) is worth the extra search step — `Proposed-governance-plan-to-DCCE.md` existed the whole time and was a strictly better answer than anything synthesized fresh.
