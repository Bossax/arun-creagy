## Honest Feedback

Three friction points worth naming. First, the "4.2" ambiguity cost more than it should have — I checked exec-summary numbering, full-report numbering, and DFR numbering before asking Boss for the literal path, when the honest move after the first miss was to ask, not keep guessing across a different numbering scheme each time. Second, the Stage 3 fork's transient API failure (`server_error`, mid-way through Call 3) was outside anyone's control, but it's worth noting the recovery worked cleanly only because the fork hadn't written anything yet — if it had partially written `draft.md` before failing, resuming would have needed more careful instruction about what to keep versus redo. Third, the lint-vs-report-naming conflict on "Governance" is not a one-off: any service or proper-noun name that happens to contain a word the lexicon has a blanket rule for will hit this same wall, and right now the fix is "stop, ask, write a sidecar note" every time. That's the correct behavior per the project's own rule-priority doctrine, but it's manual toil that will recur across all eight service headings' first mentions in other sections — an allowlist mechanism for approved bilingual proper nouns would remove a class of interruption without weakening the lexicon's general rule.

## Lessons Learned

- When a Stage 1 fork produces a unit whose justification rests partly on forward-referencing later project work (e.g. "this will be developed further in chapter 4"), that reasoning must not enter even the `warrant` or `application_to_design` fields — Stage 3 verbalizes those as prose payload, so anything written there can leak into the reader-facing draft even if no one intends it to.
- Before assuming a numbered document reference from Boss maps onto a known numbering scheme in this project (exec-summary, full-report, DFR), ask for the literal path after one failed guess rather than trying every scheme — this project layers at least three different numbering conventions and guessing across all of them wastes turns.
- A Stage 3 fork that fails mid-run with a transient API error should be resumed via `SendMessage` to the same agent rather than relaunched — it preserves whatever partial work (or, as here, correctly reports that nothing was written yet) rather than duplicating completed calls.
