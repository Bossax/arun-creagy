## Lessons Learned

1. In iterative document revision, the user's latest named subsection determines the next edit; a broader standardization plan does not override that local priority.
2. Meeting feedback should be recorded as `speaker or group → requested artifact or rule → intended user or decision`, then separated from the consultant's later synthesis.
3. Parallel subsection structure improves comparison only when chronology remains explicit: the FGD2 deck is an input to the 2.3.2 revision, while the FGD3 deck is the endpoint required for 2.3.3.
4. Data-domain changes and data-entity continuity can coexist. A concept may leave the top-level domain view while remaining represented by entities in the ERD; the prose must describe each layer separately.
5. One-paragraph commits are effective review checkpoints when each commit stages only the target document and preserves unrelated working-tree changes.
