## Key Code Changes

- `oracle-shared-skills/scripts/sync-skills.ps1` — the fix for the junction incompatibility: copies (not junctions) skill folders into `.agents\skills\`, marks every file read-only afterward so an accidental edit fails loudly instead of silently diverging and being lost on the next sync.
- `mcp-servers/scripts/lib/translate.ps1` — per-agent shape translation (`ConvertTo-AgentEntry`) and JSON smart-merge (`Merge-McpJsonFile`) that preserves unrelated keys in every agent's config file — ported the pattern from a pre-existing `oracle-bridge` skill's `syncMCP()`, extended to cover Claude's `.mcp.json` and Codex's TOML, which that original tool never handled.
- `mcp-servers/scripts/mcp-apply.ps1`'s `Write-CodexEntry` — hand-writes/merges TOML directly rather than shelling out to `codex mcp add --env`, after discovering that flag requires a literal `KEY=VALUE` (which would have baked secret values into `config.toml`, violating the registry's own "names only, never values" rule).

## Architecture Decisions

- **Junction vs. copy, decided per-agent, not globally**: `.claude\skills\` stays junctioned (proven to work), `.agents\skills\` is a copy (the only thing that works for every consumer, since Codex and Antigravity read the identical path but only one of them resolves NTFS reparse points).
- **"Last synced version is fine"** — human's explicit call, made after being offered four options (live-sync hook, release-time-only, external shared path, keep junction+detect drift). Rejected the more automated/complex options in favor of the simplest one that matches how releases already work.
- **Codex fails safe, not silent**: removing the base global `oracle-v2` and requiring an explicit `-p <Project>` was a deliberate tradeoff — a missing flag now produces an obvious "no Oracle" rather than a silent wrong-project connection, which is what the original bug was.
- **Registry lives in a plain, non-git folder** — human's explicit choice over a new git repo, prioritizing simplicity over version history for something with only 5 servers today.

## Honest Feedback

Three friction points worth naming plainly. First, I initially treated "the config file is correct" and "the agent connects" as the same fact, twice (junctions, then the `.gemini`/`.agents` path) — both times the gap was only closed because the human tested live and reported a specific, concrete symptom rather than accepting a status summary. I should weight my own untested claims about a separate running application's behavior much lower by default, not just after being corrected. Second, when asked "have you made qwen and typhoon global," I re-ran the actual status check rather than answering from memory of having done it earlier — that was the right instinct, and I'd like to name it as something to keep doing, not just the failures. Third, the session's pacing leaned heavily on the human to notice problems (they found both the skills-discovery gap and the MCP-connection gap through their own testing) rather than me proactively verifying end-to-end behavior after each build — a verification step ("did you actually restart and check X") baked into my own process, not just offered as an afterthought, would have caught at least the Antigravity path bug before it shipped.

## Lessons Learned

- **A config file having correct content is not evidence that the consuming application reads it.** Verify by testing the actual live behavior (a real connection, a real discovery scan) wherever possible, not just the file's correctness — this was the root cause of two separate bugs this session.
- **A tool's own test environment can silently differ from its documented usage environment.** The PowerShell tool always uses pwsh 7; the documented `powershell -File` command does not. Testing success in one does not transfer to the other — this cost two shipped-then-fixed bugs (`-AsHashtable`, em-dashes) in the same session.
- **When a subagent's finding is inferred from file existence/content rather than the target application's own documentation, treat it as a hypothesis, not a verified fact** — the `.gemini/mcp_config.json` path was "confirmed" by finding a pre-existing tool that wrote there, not by checking what Antigravity actually reads.
