# Iteration 4 Synthesis — What a Good Business-Requirements Package Looks Like for a Data-Platform Handoff

This iteration's objective was to ground, in requirements-engineering and enterprise-data-architecture literature, what a complete business-requirements package for an enterprise data platform should contain and how it should be organized so a pre-build blueprint phase hands off cleanly into a downstream fixed-price build phase. Both notebooks were asked the same four questions; this document compares their answers and draws conclusions for CRDB's handoff to TOR70.

## Question 1: Standard components of a well-formed business-requirements package for a data platform

Both notebooks converge on the same functional core even though they group it differently. The requirements-engineering literature organizes the package into six components — business drivers and workload profiling, an upstream source inventory with documented data caveats, a semantic mapping/business glossary, data-quality and ingestion-validation rules, role-based access control mapped to user personas, and storage tiering with lifecycle rules. The enterprise-data-architecture literature organizes a similar set of concerns into seven components — a prioritized data-product inventory, a governed business glossary sitting inside a semantic metrics layer, automated quality contracts ("data circuit breakers"), an operational governance/RACI model, mathematically verifiable non-functional requirements, security and compliance controls mapped to data classification, and a bidirectional requirements traceability matrix (RTM).

Where the two agree: a business glossary with centrally governed definitions is treated as non-negotiable by both, both insist that data-quality rules must be numeric and testable rather than generic ("data must be clean" is explicitly called out as a weak-version anti-pattern by both), and both treat access control as something that must be mapped to specific personas and data sensitivity rather than left as a flat, monolithic policy. Both also treat governance as an accountability structure with named roles (data owner, data steward), not a document that states good intentions.

Where they diverge is emphasis. The requirements-engineering literature is much more granular about the ingestion side — it details nine specific things to capture per upstream source (business impact, semantic meaning, origin, refresh frequency, historical retention, caveats, access pattern, QA rules, output schema) and gives a concrete storage-tiering/zone model (transient landing, raw, trusted, refined, sandbox). This is closer to what CRDB's data inventory and data product inventory pillars already attempt. The enterprise-data-architecture literature is more oriented toward what a downstream build team needs to be held accountable to — it is the only one of the two to introduce the bidirectional RTM and quantified, percentile-based non-functional requirements (NFRs) as standard package components, and it is the only one to describe scope discipline explicitly ("boiling-the-ocean syndrome") as a named failure mode to guard against when defining what the first phase of a data platform actually covers.

Synthesized answer for CRDB: CRDB's blueprint-phase deliverables map naturally onto the ingestion-and-glossary half of this component set — data inventory, data product inventory, and data management framework are the right place for source cataloging, glossary, quality rules, and access-pattern mapping. The RTM and quantified NFRs, which only the architecture literature treats as standard components, are correctly out of CRDB's scope per the settled phase placement (CRDB does Planning/Requirement Analysis/Design; TOR70 does Development/Testing/Deployment/Maintenance) — but that does not mean CRDB's package should be silent on the raw material those artifacts are built from. CRDB should still capture the business-outcome targets, quality thresholds, and persona/access-pattern detail that TOR70's team will need in order to construct its own RTM and NFRs later, without CRDB itself being expected to produce a formal RTM or NFR document.

## Question 2: Organizing a split engagement so the blueprint's output is directly usable as the build phase's input

Both notebooks agree that the handoff artifact must function as a signed-off, versioned baseline rather than a living or provisional document — the requirements-engineering literature is explicit that "no build team should write a single line of backend transformation logic" until stakeholders have validated sample data and formally signed off, and the architecture literature is equally explicit that requirements must be baselined at a formal review gate and placed under configuration control before development starts. Both also treat a governance/accountability model (glossary ownership, RACI-style roles) as something that must exist in the handoff package rather than be assumed.

The two notebooks diverge on document structure, and the divergence is substantive rather than cosmetic. The requirements-engineering literature models the ideal handoff as a single integrated compendium — citing a System Design Document pattern that deliberately merges requirements, user design, and data design into one baseline so the downstream team has both high-level and low-level specification in one place. The architecture literature instead recommends a structural separation modeled on IEEE Std 830 practice: the technical specification (what the system must do and how well) should be kept strictly apart from project and contractual terms (cost, delivery schedule, reporting procedures, acceptance procedures), which belong in a separate procurement Statement of Work. These are not simply two ways of saying the same thing — one treats "everything in one document" as the ideal, the other treats "keep contract mechanics out of the technical document" as the ideal. Both can be true simultaneously (one coherent content baseline, but with contractual/procurement language living in a separate instrument), and reconciling them is itself useful guidance for CRDB rather than a contradiction to resolve away.

Only the requirements-engineering literature supplies the concrete nine-question source-to-target checklist and the seven-layer logical architecture (capture, transport, refine, store, analyze, distribute, manage) as the mechanism for organizing ingestion detail. Only the architecture literature supplies the bidirectional RTM, percentile-based NFR/SLA gates, and a formal change-control board as the mechanism for organizing accountability and change discipline across the vendor boundary.

Synthesized answer for CRDB: the blueprint's output should be one coherent, cross-referenced content baseline — requirements, data design, and governance context living together so TOR70 does not have to reconcile disconnected documents — but the content that is properly TOR70's own contractual and procurement business (delivery schedule, cost, acceptance procedures, formal change control mechanics) should not be manufactured by CRDB and should stay out of CRDB's technical deliverables. CRDB's job is to make the technical and business content complete and internally consistent; the contracting mechanics belong to whoever runs TOR70's procurement.

## Question 3: What distinguishes a fixed-price-ready requirements package, and what causes fixed-price contracts to fail

Both notebooks agree, almost word for word in spirit, on the central failure mode: ambiguous, unmeasurable adjectives ("fast," "clean," "scalable," "secure") are the single most common way a requirements package fails to be fixed-price ready, because such language cannot be tested at acceptance and therefore cannot bound a vendor's liability. Both also agree that unresolved stakeholder disagreement carried into the contract, and governance structures that exist on paper without any actual enforcement mechanism (one notebook calls this "governance theater," the other calls it treating data management as a technology project rather than a business initiative), are reliable predictors of budget or scope failure.

The requirements-engineering literature's specific list of common gaps is heavily weighted toward the ingestion and pipeline side of the work: undocumented upstream data caveats and schema drift, absent numeric QA thresholds, unmapped user personas and access-latency expectations, and confusing a requirements baseline with a delivery backlog. The architecture literature's list is weighted toward contract and scope mechanics: failure to separate technical spec from procurement terms, scope that tries to cover the whole data estate at once ("boiling-the-ocean syndrome") rather than a prioritized set of critical assets, absence of a bidirectional RTM, and absence of a formal change-control gate (System Requirements Review followed by a Configuration Control Board) once the baseline is set.

Synthesized answer for CRDB: fixed-price readiness is a compound property that neither notebook alone fully covers, and CRDB's package needs both halves. The ingestion/data-quality half determines whether TOR70 can actually build the pipelines without rediscovering source-system quirks mid-contract; the scope/traceability half determines whether TOR70's fixed price will hold once built. CRDB is well positioned to close the first half through its data inventory and gap-analysis pillars. The second half — bounding scope to a prioritized set of use cases rather than "all eight products at once," and giving TOR70 enough traceability from business need to functional requirement — depends heavily on the use-case prioritization step that is explicitly part of DCCE's accepted 3-step handoff process, which reinforces that prioritization is not a nice-to-have but a direct lever on fixed-price viability.

## Question 4: How use-case prioritization, service/content design, and governance sign-off fit into the package

The requirements-engineering literature frames this question in terms of which document each element lives in: use-case prioritization is an integrated component inside the core requirements document (it cites a concrete 1-to-5 priority rating scheme — Critical, High, Medium, Low, Future — used to distinguish what an MVP needs from what can be deferred); service/content design is likewise integrated, bundled with the technical requirements into a single compendium (user design and data design co-located with functional requirements); and governance is treated differently from the other two — it is scoped as a distinct, standalone deliverable, with sign-off functioning as a hard gate ("do not start work on transformation logic until you get sign-off").

The architecture literature frames the same question in terms of when each element happens in a phased sequence: use-case prioritization is the core output of a discovery/assessment phase (identifying a bounded set of critical data assets, not the whole estate); service/content design spans a design phase and early build integration, expressed through data-product usability criteria (discoverable, addressable, understandable, trustworthy, accessible, interoperable, secure) and formal external-interface specification; and governance sign-off is the decision gate that closes the design phase, formalized through a governance council and RACI matrix, with a review milestone that places the baseline under change control afterward.

These two framings do not conflict — one answers "which artifact," the other answers "when" — and together they are more useful to CRDB than either alone. Both notebooks independently and without prompting arrive at the same conclusion on governance specifically: it is not folded into the general requirements narrative the way service/content design is, and it functions as a formal sign-off gate rather than an ongoing responsibility. This directly corroborates DCCE's already-accepted 3-step handoff process, where governance-framework certification is its own explicit step rather than an implicit property of the other two steps.

Synthesized answer for CRDB: use-case prioritization and service/content design belong inside CRDB's integrated requirements/use-case output as components, sequenced early (discovery-equivalent) and mid-phase (design-equivalent) respectively; governance-framework sign-off should remain a separate, clearly delineated deliverable with its own review and certification step, consistent with DCCE's step (c). This is a confirmation rather than a new finding — DCCE's process, agreed on before this research began, is exactly what both bodies of literature independently recommend.

### 2. Real-World & Industry Practice Sanity Check
Web search cross-referencing against enterprise data platform fixed-price contracts and IEEE 830 handoff practices confirms the synthesis is highly accurate, but highlights two specific industry nuances worth refining:

- **Business NFRs vs. System NFRs (Gap in Q1/Q2):** The synthesis concludes that NFRs (Non-Functional Requirements) are "correctly out of CRDB's scope." In real-world data engineering handoffs, a strict distinction is made. **System NFRs** (e.g., index strategies, node sizing) belong to the builder (TOR70). However, **Business NFRs** (e.g., data freshness SLAs < 24h, regulatory PDPA compliance, uptime for critical pipelines) MUST be defined in the blueprint phase by the business analyst/architect (CRDB). CRDB should own the Business NFRs directly, not just the "raw material."
- **Mitigating the "Illusion of Certainty" (Enhancement for Q3):** The synthesis correctly identifies ambiguous adjectives as the primary fixed-price killer. Industry practice standardizes the mitigation of this through two specific artifacts: **Data Contracts** (formalizing schema and quality expectations) and an **Explicit Assumption Log** (e.g., "Assumes API rate limits allow X requests/min"). CRDB's package should explicitly include an Assumption Log to bound vendor liability and prevent scope creep.
- **Technical Spec vs. SOW Separation:** The synthesis's observation to separate technical requirements from the procurement Statement of Work (SOW) aligns perfectly with IEEE 830/ISO 29148 best practices. Handoffs succeed when technical specs are a unified baseline, while commercial/acceptance terms live in the SOW.
