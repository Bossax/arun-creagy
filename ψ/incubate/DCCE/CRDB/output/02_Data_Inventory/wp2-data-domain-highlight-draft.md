# WP2 Data Domain Highlight — A-BTR + Disaster-Loss-Statistics (Draft)

## 1. Purpose, Scope, Methodology

**Purpose**: This document is a scoped-down replacement for the earlier, over-broad WP2 Stage A/B exercise (`wp2-demand-signals-draft.md` + `wp2-catalog-scoring-draft.md`, kept as reference/history, not overwritten). It combines demand-signal extraction and catalog matching into one pass, covering **exactly two priority use cases**: **A-BTR** (Thailand's Biennial Transparency Report adaptation chapter, drawn from the `A-BTR_requirement_analysis` CSV set) and **disaster-loss-statistics** (D-043 Service 4 — Historical Loss & Damage Assessment, signals #19–24, reused verbatim from `wp2-demand-signals-draft.md`). No other use case or service is in scope.

**Methodology summary**: For A-BTR, all 379 rows of `requirement_statement.csv` were read and filtered to requirement rows that imply a concrete, nameable data/variable need (named metric, indicator, index, geographic breakdown, time series, hazard/exposure/vulnerability measure, or institutional/M&E dataset) — process/governance-only rows with no data shape were excluded. Selected rows were joined to their linked evidence quote via `requirement_evidence_link.csv` → `evidence_unit.csv` (confirmed 1:1 sequential mapping between requirement rows and evidence-unit rows) and, where applicable, to `quantitative_value.csv`. Each candidate signal (A-BTR + disaster-loss-statistics) was then checked against `data_catalog_v4.csv` (262 dataset rows) using `title`, `cdm_data_entity`, `cdm_domain`, `related_hazards`, `sectors`, `spatial_resolution`, and `temporal_resolution`/`time_period_start`/`time_period_end` as match evidence; `access_rights_dataset`, `use_limitations`/`notes`, and `endorsement_status`/`validation_flag` were used only to grade fitness of a match already made on the above fields, never to establish the match itself; `high_value_dataset`, `tag_string`, `data_category`, and `license_id` were treated as secondary corroboration only, per the explicit prohibition on scoring off a catalog's own self-tags.

**This replaces the earlier broader-scope draft**: the previous exercise scored the full ~260-row catalog against all 8 D-043 services and 34 use cases with no A-BTR input. This draft is intentionally narrower — two priority use cases only — but goes deeper on each: full-document extraction with evidence citation, rather than narrative-topic listing.

## 5. Aggregated Highlight — Catalog Datasets Supported by These Two Priority Use Cases

Datasets/dataset-clusters below are those with **Direct** or **Partial** confidence from at least one A-BTR or disaster-loss-statistics signal (Inferred-only support is listed separately at the end for transparency, not silently dropped).

**Strongly supported (Direct match from multiple independent signals):**
1. `DCCE_3_1`–`DCCE_3_7` (CCIC composite risk indices, `https://ccic.dcce.go.th/riskarea`) — supported by A-REQ-016, B-REQ-099, D-REQ-032, F-REQ-001/002. Fitness caveat: `use_limitations` shows scenario coverage is SSP5-8.5-plus-one-other-SSP per row, not the full dual-scenario set the source text implies. **Boss review — role caveat**: `DCCE_3_1`–`3_7` function as a *gold-layer / policy-communication* product, not reusable platform infrastructure. ## 6. Open Ambiguities for Boss / Oracle Lookup

1. **Are `DCCE_3_1`–`DCCE_3_7` the same thing as the "Yearly Vulnerability Index" and "Climate Resilience Index" named in D-REQ-048/049 (EVU-277/278)?** The catalog rows are composite Hazard×Exposure×Vulnerability indices per province, hosted at the same CCIC URL the evidence text cites for the Climate Risk Map Database, and conceptually overlap the exposure/sensitivity/coping-capacity taxonomy in D-REQ-047. But no catalog field names them "Yearly Vulnerability Index" or "Climate Resilience Index" specifically, and the BTR text describes a *two-stage* monitoring→evaluation pipeline (annual index → multi-year trend synthesis) that the catalog's flat per-provider index rows do not obviously distinguish. This could not be resolved from the two source documents alone — genuinely unresolvable without asking DCCE/CCIC directly whether these are the same product under different names, or two different things.

2. **Is `TMD_4_1`/`TMD_3_1` (cyclone track data) ever going to become available?** `use_limitations` says *"อยู่ระหว่างขอข้อมูล - ยังไม่ได้รับ"* (request pending, not yet received) as of catalog v4's snapshot date. Since B-REQ-057–063's entire cyclone-frequency/seasonality/projection signal cluster has no better catalog candidate, whether this dataset materializes materially changes the A-BTR cyclone-hazard section's data-supply picture. Flagging for Boss/Oracle follow-up rather than guessing a resolution date. **Resolved per Boss review**: this dataset should be requestable — the gap is an acquisition/follow-up action, not a fundamental unavailability. Recommend flagging this as an actionable data-request item (WP8) rather than a standing gap.

3. **Does the catalog's `DDPM_2_1`/`DDPM_2_3` disaster-record pair, once cleaned up (per the `use_limitations` field's own stated need for "AI tools to clean data" and UNDRR-taxonomy alignment), become the authoritative source for the A-BTR's Table 1-2 (B-REQ-091) and for Track-2 disaster-loss-statistics signals #19–21 collectively?** This is the highest-value convergence point found in this whole matching pass (see §5), but whether DDPM's internal remediation roadmap for these known issues is scheduled/funded is outside what either source document states — this is a governance/planning question for Boss, not an extraction question. **Boss review**: this should be framed as a concrete recommendation, not left open — a data pipeline that cleans/standardizes the DDPM_2_1/2_3 records could be proposed as the basis for a disaster-statistics summary service (candidate WP8 recommendation).
4. **B-REQ-030/031's CORDEX-Southeast-Asia RegCM5.0 25×25km SST projection product**: the evidence text (EVU-067) is very specific about model ensemble (EC-Earth3-Veg, MIROC6, CMCC-ESM2), downscaling method (RegCM5.0), and resolution (25×25km) — none of which appears in `GISTDA_2_1`'s (the only SST-tagged catalog row) metadata, which is an *observed* satellite SST product (VIIRS), not a projection. It is unclear whether this projected-SST product exists anywhere in DCCE's holdings under a name/owner-org not yet in `data_catalog_v4.csv`, or whether it is a report-only figure with no standing dataset behind it. Flagged rather than assumed either way. **Resolved per Boss review**: `GISTDA_2_1` is confirmed observation data, not a projection product — this is a confirmed catalog gap (no projected-SST product present), not an unresolved ambiguity.

5. **F-REQ-036's evidence-unit linkage (EVU-375) is a bare section header, not substantive text** — see §2.9, item 122. The requirement statement itself is clearly data-shaped, but its cited evidence excerpt does not actually support it with content. This looks like either a CSV linkage/alignment artifact in the source A-BTR extraction pipeline (upstream of this task) or a genuine case where the underlying report placed the data-availability-constraint claim in prose not captured by the evidence-unit segmentation. Not resolvable from the files available here; noted rather than silently patched over by substituting other evidence.
