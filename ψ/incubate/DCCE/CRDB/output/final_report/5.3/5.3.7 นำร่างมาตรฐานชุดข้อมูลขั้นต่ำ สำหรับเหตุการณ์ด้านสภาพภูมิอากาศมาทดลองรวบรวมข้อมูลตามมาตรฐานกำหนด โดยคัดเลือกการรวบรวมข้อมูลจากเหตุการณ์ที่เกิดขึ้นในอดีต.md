### 5.3.7 นำร่างมาตรฐานชุดข้อมูลขั้นต่ำ สำหรับเหตุการณ์ด้านสภาพภูมิอากาศมาทดลองรวบรวมข้อมูลตามมาตรฐานกำหนด โดยคัดเลือกการรวบรวมข้อมูลจากเหตุการณ์ที่เกิดขึ้นในอดีต

การนำร่างมาตรฐานชุดข้อมูลขั้นต่ำมาทดลองใช้กับเหตุการณ์ที่เกิดขึ้นในอดีตในหัวข้อนี้ มีวัตถุประสงค์เป็นการทดสอบวิธีวิทยาและการปรับเทียบแบบจำลองข้อมูล มิใช่การย้อนกลับไปสร้างฐานข้อมูลประวัติภัยพิบัติฉบับสมบูรณ์ของประเทศ ขอบเขตของการทดลองจึงต้องถูกกำหนดให้ชัดตั้งแต่ต้นว่าเป็นการนำ MVD ที่ออกแบบไว้แล้วมาทดสอบกับเอกสารเหตุการณ์จริง เพื่อดูว่าฟิลด์ใดเก็บได้จริงตั้งแต่ชั้นรายงานด่วน ฟิลด์ใดต้องอาศัยเอกสารหรือการประเมินในระยะต่อมา และฟิลด์ใดยังไม่มีระบบข้อมูลรองรับในทางปฏิบัติ การกำหนดขอบเขตเช่นนี้สำคัญมาก เพราะทำให้ผลการทดลองถูกตีความในฐานะข้อมูลย้อนกลับเพื่อปรับปรุงแบบจำลอง ไม่ใช่ในฐานะคำอ้างว่าประเทศได้สร้างฐานข้อมูลย้อนหลังครบถ้วนแล้ว

เหตุการณ์ตัวอย่างที่ใช้ทดสอบจึงไม่จำเป็นต้องมีจำนวนมาก แต่ต้องคัดเลือกอย่างมีเหตุผลให้เพียงพอต่อการเปิดเผยข้อจำกัดของแบบจำลอง เช่น เลือกเหตุการณ์ที่ต่างประเภทภัย ต่างพื้นที่ หรือมีรูปแบบเอกสารประกอบต่างกันพอสมควร หลักเกณฑ์สำคัญกว่าจำนวนคือความเพียงพอของร่องรอยเอกสาร เพราะหากเหตุการณ์ไม่มีรายงานด่วน รายงานติดตามผล แบบฟอร์มภาคสนาม หรือบันทึกสรุปจากหน่วยงานที่เกี่ยวข้องเพียงพอ การทดลองจะกลายเป็นการเดาข้อมูลมากกว่าการทดสอบ MVD ดังนั้น การคัดเลือกควรให้น้ำหนักกับเหตุการณ์ที่มีเอกสารต้นทางใช้แมปเข้าสู่ฟิลด์ต่าง ๆ ได้จริง แม้จะเป็นเพียงชุดเล็กของเหตุการณ์ก็ตาม ความเป็นตัวแทนในที่นี้จึงเป็นความเป็นตัวแทนเชิงวิธีวิทยา ไม่ใช่ความเป็นตัวแทนเชิงสถิติของเหตุการณ์ทั้งประเทศ

ลำดับการทดสอบควรเริ่มจากการรวบรวมเอกสารของแต่ละเหตุการณ์ให้เป็นแพ็กข้อมูลเดียวกันก่อน แล้วจึงดำเนินการแมปข้อมูลเข้าสู่โครงสร้างของ MVD ตามชั้นตรรกะที่ออกแบบไว้ โดยต้องเริ่มจาก event header หรือแกนข้อมูลเหตุการณ์ขั้นต่ำก่อนเสมอ ได้แก่ รหัสเหตุการณ์ ประเภทภัย วันที่หรือช่วงเวลา พื้นที่เกิดเหตุ รหัสหน่วยพื้นที่ แหล่งรายงาน หน่วยงานที่รายงาน และผลกระทบขั้นต้น เช่น ผู้ได้รับผลกระทบ ผู้บาดเจ็บ ผู้เสียชีวิต ความเสียหายต่อที่อยู่อาศัย หรือผลกระทบต่อบริการสาธารณะ หาก event header ยังไม่สามารถเติมได้อย่างมีวินัยจากเอกสารจริง ก็ย่อมสะท้อนทันทีว่า minimum core ของ MVD ยังเกินขีดความสามารถของระบบรายงานที่มีอยู่ แต่หากชั้นนี้เติมได้สม่ำเสมอ จึงค่อยขยับไปทดสอบชั้นข้อมูลผลกระทบที่ละเอียดขึ้น

ในการแมปข้อมูล ต้องหลีกเลี่ยงการยุบข้อมูลทั้งหมดให้กลายเป็นหนึ่งแถวหรือหนึ่งระเบียนรวม เพราะจะทำซ้ำปัญหาเชิงแนวคิดที่แบบจำลองพยายามแก้ไขอยู่เดิม การทดสอบควรแยก observation หรือระเบียนผลกระทบตามประเภทอย่างน้อยระหว่างผลกระทบต่อคน ผลกระทบต่อทรัพย์สิน ผลกระทบต่อบริการสาธารณะ ผลกระทบเฉพาะภาคส่วน และค่าประเมินทางการเงินที่เกิดจากวิธีคำนวณต่างกัน หากเอกสารชุดเดียวกันให้ข้อมูลหลายมิติ ก็ควรแมปเป็นระเบียนที่เชื่อมกับ event header เดียวกัน ไม่ใช่นำทุกค่ามารวมเป็น “ผลกระทบรวม” ก้อนเดียว เพราะนอกจากจะทำให้โครงสร้างข้อมูลสูญเสียความหมายแล้ว ยังปิดโอกาสในการตรวจสอบว่าแต่ละค่ามาจากวิธีรายงานหรือวิธีประเมินคนละแบบกัน

เครื่องมือสำคัญของการทดสอบในหัวข้อนี้คือการให้คะแนนสถานะความพร้อมของแต่ละฟิลด์แบบสามทาง ได้แก่ required-now, later-completion และ not-currently-available หรือในความหมายไทยคือ “มีได้ทันทีจากระบบรายงานปัจจุบัน”, “มีแนวทางเติมได้ในระยะต่อมา”, และ “ยังไม่มีฐานข้อมูลหรือกลไกรองรับในปัจจุบัน” การจำแนกเช่นนี้ทำให้การทดสอบไม่ถูกลดรูปเป็นการตัดสินแบบผ่าน–ไม่ผ่าน หากแต่กลายเป็นการวิเคราะห์จังหวะการเกิดข้อมูลในระบบจริง ฟิลด์ที่ได้คะแนน required-now อย่างสม่ำเสมอในหลายเหตุการณ์ควรได้รับการยืนยันให้คงอยู่ใน minimum mandatory core ฟิลด์ที่มักปรากฏจากรายงานติดตามผล เอกสารภาคส่วน หรือการประเมินภายหลัง ควรถูกจัดเป็น later-completion modules ส่วนฟิลด์ที่แทบไม่ปรากฏเลยควรถูกทบทวนอย่างจริงจังว่าเป็นความต้องการเชิงนโยบายที่ยังไม่มีโครงสร้างรองรับ หรือเป็นการตั้งความคาดหวังที่ยังไม่เหมาะกับระบบปัจจุบัน

การจับ provenance ต้องเป็นส่วนหนึ่งของผลการทดสอบ ไม่ใช่ภาคผนวกทางเอกสาร กล่าวคือ ทุกฟิลด์ที่ถูกแมปควรบันทึกอย่างน้อยว่าได้มาจากเอกสารใด หน่วยงานใด ในช่วงเวลาการรายงานใด และเป็นข้อมูลระดับรายงานด่วน รายงานติดตามผล หรือการประเมินเชิงลึกภายหลัง หากเป็นค่าประมาณหรือค่าที่คำนวณขึ้น ควรบันทึกวิธีได้มาของค่านั้นด้วย เพราะเป้าหมายของการทดลองไม่ได้อยู่ที่การหา “ค่าที่ถูกที่สุด” เพียงค่าเดียว แต่อยู่ที่การพิสูจน์ว่า MVD สามารถรักษาร่องรอยที่มาของข้อมูลได้หรือไม่ เมื่อระบบในอนาคตต้องเชื่อมข้อมูลหลายแหล่งเข้าด้วยกัน provenance จึงเป็นส่วนหนึ่งของคุณภาพเชิงโครงสร้างของแบบจำลอง ไม่ใช่เพียงความเรียบร้อยในการจดบันทึก

ในทำนองเดียวกัน หากพบว่าข้อมูลจากหลายเอกสารให้ค่าต่างกัน การจัดการที่ถูกต้องไม่ใช่การเฉลี่ยหรือเลือกค่าหนึ่งอย่างเงียบ ๆ เพื่อให้ตารางดูสะอาด แต่ต้องคงความแตกต่างนั้นไว้และตีความในฐานะหลักฐานเชิงระบบ ความไม่ตรงกันของตัวเลขอาจสะท้อนการรายงานคนละช่วงเวลา การใช้นิยามไม่ตรงกัน การนับคนละหน่วย หรือการขาดจุดควบคุมคุณภาพในกระบวนการรายงานปัจจุบัน การรักษาความแตกต่างเหล่านี้จึงมีคุณค่าต่อการออกแบบ revision control, validation workflow และกฎการยืนยันข้อมูลใน MVD รุ่นปรับปรุง เพราะทำให้ทีมออกแบบเห็นว่าปัญหาไม่ได้อยู่ที่ข้อมูล “ผิด” เพียงอย่างเดียว แต่อยู่ที่ระบบยังไม่มีตรรกะพอในการบอกว่าค่าใดเป็นค่าเบื้องต้น ค่าใดเป็นค่าที่ตรวจสอบแล้ว และค่าใดเป็นค่าประเมินภายหลัง

ตรรกะของ PDNA มีบทบาทสำคัญต่อการตีความผลการทดลอง โดยเฉพาะในการอธิบายว่า later-completion หมายถึงอะไรในเชิงเนื้อหา มิใช่เพียงข้อมูลที่ยังหาไม่เจอ PDNA แสดงให้เห็นว่า baseline data, detailed damage sheets, loss calculations, verification records และ recovery-needs blocks เป็นองค์ประกอบของการประเมินระยะหลังที่เกิดขึ้นเมื่อพ้นช่วงฉุกเฉินแล้ว ดังนั้น หากฟิลด์เหล่านี้ไม่ปรากฏในรายงานด่วนของเหตุการณ์ตัวอย่าง ก็ไม่ควรสรุปว่าแบบจำลองออกแบบเกินจริงเสมอไป แต่อาจเป็นข้อยืนยันเชิงวิธีวิทยาว่าฟิลด์ดังกล่าวควรถูกจัดไว้ในโมดูลระยะหลังตามตรรกะ phased completion ของ MVD การทดสอบจึงต้องแยกให้ออกระหว่าง “ไม่มีเพราะไม่จำเป็นในระยะต้น” กับ “ไม่มีเพราะระบบยังไม่พร้อมรองรับ” ซึ่งเป็นข้อสรุปคนละแบบและนำไปสู่การปรับแบบจำลองคนละทิศทาง

ผลการทดสอบควรถูกสรุปในฐานะการ calibrate MVD ไม่ใช่การประเมินความสมบูรณ์ของเหตุการณ์ในอดีต กล่าวคือ หากฟิลด์ใดสามารถเติมได้ต่อเนื่องในเหตุการณ์หลายประเภท ฟิลด์นั้นควรถูกยืนยันเป็นแกนบังคับขั้นต่ำของแบบฟอร์ม หากฟิลด์ใดเติมได้เฉพาะเมื่อมีเอกสารภาคส่วนหรือมีการประเมินเพิ่มเติม ฟิลด์นั้นควรถูกย้ายไปอยู่ใน later-completion modules พร้อมกำหนดแหล่งข้อมูลและหน่วยงานเจ้าของข้อมูลที่เหมาะสม และหากฟิลด์ใดแทบไม่มีโอกาสเติมได้จากระบบข้อมูลปัจจุบัน ก็ควรถูกพิจารณาว่าจะตัดออกจากรอบปัจจุบัน ชะลอไว้ในแผนพัฒนาระยะถัดไป หรือระบุเป็นช่องว่างเชิงสถาบันที่ต้องลงทุนแก้ไขต่อไป กระบวนการอ่านผลเช่นนี้จะทำให้ MVD ถูกปรับให้สอดคล้องกับความเป็นจริง มากกว่าจะคงไว้ซึ่งความครบถ้วนเชิงทฤษฎีที่ไม่สามารถปฏิบัติได้

กล่าวโดยสรุป การทดลองในหัวข้อนี้เป็นวิธีการตรวจสอบแบบจำกัดขอบเขตที่ใช้เหตุการณ์ในอดีตเป็นสนามทดสอบของ MVD เพื่อดูว่าแบบจำลองที่เสนอมีความเป็นไปได้เพียงใดภายใต้ระบบรายงานจริงของไทย วิธีการที่ถูกต้องจึงต้องประกอบด้วยการคัดเลือกเหตุการณ์อย่างมีเหตุผล การรวบรวมเอกสารต้นทาง การแมปเข้าสู่ event header และ repeated observations การให้คะแนนสถานะความพร้อมของฟิลด์ การบันทึก provenance ในระดับฟิลด์ การรักษาความต่างระหว่างแหล่งข้อมูล และการนำผลลัพธ์กลับไปปรับสมดุลระหว่าง required-now core กับ later-completion modules เมื่อดำเนินการเช่นนี้ การทดสอบจะไม่ใช่เพียงการพิสูจน์ว่า “กรอกได้หรือไม่ได้” แต่จะกลายเป็นกลไกสำคัญที่ผูกการออกแบบ MVD ในหัวข้อก่อนหน้าเข้ากับวิธีใช้จริงในระบบรายงานและการประเมินของประเทศ
