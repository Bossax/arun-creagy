## บันทึกหลักฐานประกอบการร่างหมวด 5.3.3, 5.3.8 และ 5.3.9

วันที่จัดทำ: 25 มิถุนายน 2569  
ขอบเขตหลักฐานที่ใช้: โฟลเดอร์ `02_UseCases_FunctionalSpecs` และ `consultation_workshop` เท่านั้น

### 1. เอกสารหลักที่ใช้เป็นฐานข้อเท็จจริง

1. รายงานสรุปความต้องการใช้งานบริการข้อมูลสารสนเทศด้านภูมิอากาศ ซึ่งสังเคราะห์ความต้องการจากการสัมภาษณ์และ workshop ไปสู่บริการข้อมูลสารสนเทศ 8 บริการ
2. รายงานการวิเคราะห์ช่องว่างข้อมูลเชิงโครงสร้างและประเด็นการดำเนินงานเชิงยุทธศาสตร์ ซึ่งประเมินบัญชีข้อมูลกลางมากกว่า 260 รายการ และชี้ว่ามีเพียงประมาณร้อยละ 20 ที่พร้อมใช้ตอบโจทย์ผู้ใช้ ขณะที่ร้อยละ 80 ยังติดข้อจำกัดด้านความละเอียด การเข้าถึง การรับรอง และการแปลงข้อมูล
3. ตารางวิเคราะห์รวมกิจกรรมที่ 2 ของ workshop ซึ่ง normalize แนวคิดบริการ 26 แนวคิดของผู้เข้าร่วมและโยงเข้าสู่ canonical use cases
4. เอกสาร demand clustering ซึ่งจัดลำดับคลัสเตอร์ความต้องการหลักและ hardening priorities ของระบบ
5. เอกสาร canonical use cases ซึ่งทำหน้าที่เป็นชั้นกลางระหว่างเสียงสะท้อนรายหน่วยงานกับการสังเคราะห์บริการ

### 2. สรุป stakeholder needs และ workshop outcomes

#### 2.1 ความต้องการร่วมที่ปรากฏซ้ำ

1. ต้องการค่าฐานหรือชุดข้อมูลอ้างอิงกลางที่มีสถานะทางการและใช้ร่วมกันได้
2. ต้องการข้อมูลเชิงพื้นที่ระดับตำบล เทศบาล สินทรัพย์รายจุด หรือระดับย่อยกว่า เพื่อรองรับงานปฏิบัติการจริง
3. ต้องการรูปแบบบริการมากกว่าไฟล์ เช่น API, dashboard, usage guide, คู่มือการตีความ และ data package สำหรับการตัดสินใจ
4. ต้องการข้อมูลย้อนหลังระยะยาวควบคู่ข้อมูลคาดการณ์อนาคต เพื่อเชื่อม baseline กับ foresight
5. ต้องการกรอบการประเมินความสูญเสียและความเสียหายเชิงเศรษฐกิจที่มีมาตรฐาน
6. ต้องการมาตรฐานการสื่อสารความไม่แน่นอนเพื่อให้ผู้บริหารและผู้ใช้งานใช้ข้อมูลคาดการณ์ได้อย่างปลอดภัย

#### 2.2 ข้อสรุปสำคัญจาก workshop consolidation

- แนวคิดบริการจากผู้เข้าร่วม 26 แนวคิด สามารถโยงเข้าสู่ canonical use case ได้ 20 แนวคิด หรือประมาณร้อยละ 77 จึงสะท้อนว่าโครงสร้าง use case เดิมสอดคล้องกับโจทย์ภาคสนามในระดับสูง
- แนวคิดใหม่ที่ยังไม่ถูกรองรับเต็มที่มี 6 ประเด็น เช่น หลุมยุบ ความหลากหลายทางชีวภาพทางทะเล คุณภาพน้ำทะเล และเกณฑ์เตือนภัยเฉพาะพื้นที่
- workshop จึงทำหน้าที่ 3 ชั้น คือ 1) ยืนยันความต้องการซ้ำจากการสัมภาษณ์ 2) จัดระเบียบความต้องการเป็น use case ที่ตรวจสอบได้ และ 3) ชี้ว่าระบบควร harden บริการแกนกลางบางประเภทก่อน แทนที่จะพัฒนาระบบเฉพาะกิจจำนวนมาก

### 3. Prioritized use cases และ service focus

จาก demand clustering สามารถสรุปคลัสเตอร์ความต้องการหลักได้ 5 กลุ่ม

1. **Authoritative Baselines & SSOT** — ต้องการแหล่งข้อมูลอ้างอิงกลางและค่าฐานที่ยอมรับร่วมกัน
2. **Localized Vulnerability & Risk** — ต้องการแผนที่ความเสี่ยงและความเปราะบางระดับตำบลหรือย่อยกว่า
3. **Sectoral Impact & Standards** — ต้องการมาตรฐานและวิธีคำนวณสำหรับการเงิน การงบประมาณ การท่องเที่ยว และโครงสร้างพื้นฐาน
4. **Urban Resilience & Land Use** — ต้องการข้อมูลเชิงพื้นที่เพื่อผังเมือง เมืองฟองน้ำ และการจัดการความร้อนเมือง
5. **New Domain Frontiers** — ต้องการรองรับโจทย์ใหม่ที่อยู่นอกเมนูเดิม

ลำดับความสำคัญเชิงยุทธศาสตร์ในระยะต้นควรเริ่มจาก 3 แกนก่อน ได้แก่

1. ค่าฐานกลางและการรับรองข้อมูลทางการ
2. ความเสี่ยงและความเปราะบางระดับพื้นที่ที่ละเอียดพอใช้จริง
3. มาตรฐานและหลักฐานสนับสนุนสำหรับการตัดสินใจรายสาขา โดยเฉพาะด้านงบประมาณ การเงิน และวิศวกรรม

เมื่อจับคู่กับบริการข้อมูลสารสนเทศ 8 บริการ จะพบว่าแกนดังกล่าวเชื่อมตรงกับบริการ 1, 2, 3, 5 และ 8 มากที่สุด ส่วนบริการ 4, 6 และ 7 เป็นบริการขยายผลเชิงระบบ

### 4. Readiness signals และ data-set gaps

#### 4.1 สัญญาณ readiness

- ประเทศไทยมีข้อมูลต้นทางจำนวนมาก ทั้งข้อมูลภัย ข้อมูลอุตุนิยมวิทยา ข้อมูลดาวเทียม และข้อมูลเชิงพื้นที่จากหลายหน่วยงาน
- ผู้ใช้จำนวนมากพร้อมใช้บริการดิจิทัล เช่น API, web service และ dashboard เฉพาะภารกิจ
- workshop สะท้อนว่ามีอุปสงค์ชัดเจนต่อระบบ single source of truth และบริการที่ผูกกับ workflow จริง

#### 4.2 ช่องว่างเชิงโครงสร้างที่สำคัญ

1. มีเพียงร้อยละ 20 ของข้อมูลที่พร้อมตอบโจทย์ผู้ใช้จริง
2. ข้อมูลส่วนใหญ่ยังละเอียดเพียงระดับประเทศหรือจังหวัด ขณะที่โจทย์จำนวนมากต้องใช้ระดับตำบลหรือสินทรัพย์รายจุด
3. ร้อยละ 80 ของข้อมูลยังเข้าถึงแบบจำกัดและต้องประสานงานรายครั้ง
4. ข้อมูลจำนวนมากยังอยู่ในรูป PDF หรือ spreadsheet และขาด metadata, data dictionary, lineage, รอบอัปเดต และเงื่อนไขการใช้
5. หลายบริการไม่ขาดข้อมูลต้นทาง แต่ขาดเครื่องมือหรือระเบียบวิธีแปลงข้อมูลวิทยาศาสตร์ให้เป็นข้อมูลใช้งานจริง
6. ข้อมูลความเปราะบาง สินทรัพย์ และข้อมูลรายสาขายังอ่อนกว่าข้อมูลภัยอย่างมีนัยสำคัญ
7. ยังไม่มีมาตรฐานกลางในการสื่อสารความไม่แน่นอนและสถานะความพร้อมของข้อมูล

### 5. Recommendation logic ที่เชื่อมไปสู่หมวด 5.3.9

#### 5.1 Data governance

ความต้องการชุดข้อมูลอ้างอิงกลางและข้อจำกัดเรื่อง metadata การรับรอง และที่มาของข้อมูล ชี้ว่าข้อเสนอเชิงนโยบายต้องเริ่มจากกรอบ data governance ภายใน DCCE ที่ชัดเจน ทั้ง data owner, data steward, metadata minimum, data dictionary และกติกาการรับรองข้อมูลอ้างอิง

#### 5.2 Internal management policy

หลักฐานชี้ว่า DCCE ไม่ควรบริหาร CRDB ในฐานะโครงการไอทีหรือคลังไฟล์แบบแยกส่วน แต่ควรบริหารในฐานะ service portfolio ที่มี product owner, service owner, roadmap และรอบทบทวนความต้องการผู้ใช้

#### 5.3 Technical standards

จำเป็นต้องมีอย่างน้อย 4 ชั้นมาตรฐานร่วม ได้แก่ 1) data standard 2) metadata and lineage standard 3) interoperability standard เช่น API/web service 4) uncertainty communication standard

#### 5.4 Technical partnerships

หลายบริการต้องอาศัยข้อมูลและความเชี่ยวชาญจากหน่วยงานอื่น เช่น น้ำ สถิติ เศรษฐกิจ การเงิน โครงสร้างพื้นฐาน และระบบเตือนภัย จึงต้องมี partnership ในรูป data-sharing, co-development และ method co-creation

#### 5.5 Competitive positioning ของ DCCE

DCCE ควรวางตำแหน่งตนเองเป็น 1) ผู้กำหนดมาตรฐาน 2) ผู้รับรองและจัดระเบียบชุดข้อมูลอ้างอิง 3) ผู้ประสานการแปลงข้อมูลวิทยาศาสตร์สู่บริการใช้งานจริง และ 4) ผู้สร้าง institutional shield ให้การตัดสินใจภาครัฐและภาคีใช้ข้อมูลที่น่าเชื่อถือได้อย่างปลอดภัย
