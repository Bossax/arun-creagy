 
# CRDB Workshop Output Analysis Plan

## 1. Purpose

This plan defines how to analyze the outputs in [`ψ/incubate/DCCE/CRDB/output/consultation_workshop/result/`](ψ/incubate/DCCE/CRDB/output/consultation_workshop/result/) from the consultation workshop Activity 2.

The goal is to convert mixed-format workshop outputs into a structured, traceable analysis that reveals:

1. what kinds of climate services participants actually want,
2. what decisions those services are expected to support,
3. what data and presentation forms are required,
4. what institutional and technical barriers repeatedly appear, and
5. which service concepts are most salient under the three workshop voting lenses.

This plan is grounded in:

- the final Activity 2 design actually used in the workshop,
- the long use-case menu in [`ψ/incubate/DCCE/CRDB/output/consultation_workshop/user_use_case_raw.md`](ψ/incubate/DCCE/CRDB/output/consultation_workshop/user_use_case_raw.md),
- the mixed-format workshop outputs in [`ψ/incubate/DCCE/CRDB/output/consultation_workshop/result/`](ψ/incubate/DCCE/CRDB/output/consultation_workshop/result/), and
- the methodological note [`ψ/incubate/DCCE/CRDB/inbox_note/Qualitative-analysis-of-workshop-output.md`](ψ/incubate/DCCE/CRDB/inbox_note/Qualitative-analysis-of-workshop-output.md).

## 3. Analytical reconstruction of the actual Activity 2 protocol

Activity 2 should be analyzed according to the workshop format actually used:

1. participants were shown a long menu of pre-constructed use cases from [`user_use_case_raw.md`](ψ/incubate/DCCE/CRDB/output/consultation_workshop/user_use_case_raw.md),
2. each participant selected one use case that best fit their needs or created a new one,
3. for the chosen concept, each participant/group answered three questions:
   - objective: what is the service for and what question does it answer,
   - requirements: what data/information and what forms of presentation are needed,
   - challenges: what makes the service difficult to build,
4. participants then voted using colored stickers:
   - orange = most answers their own needs,
   - pink = most answers everyone’s needs,
   - green = most suitable for DCCE to tackle first.

The analysis must preserve these as three distinct evaluative lenses rather than collapsing them immediately into one total score.

---

## 4. Core analytical questions

The analysis should answer the following:

1. What kinds of climate service concepts are stakeholders prioritizing?
2. Which decisions or work tasks do they want these services to support?
3. Are participants asking mainly for raw data, interpreted products, integrated platforms, standards, or institutional coordination?
4. What recurring barriers appear across sectors and agencies?
5. Which concepts have:
   - high individual fit,
   - high collective relevance,
   - high DCCE tractability?
6. Where do participants reveal shallow, partial, or advanced understandings of “climate services”?
7. What implications do these findings have for CRDB deliverables, NCAIF design, governance, and FGD3 ratification?

---

## 5. Proposed analysis framework

Use a five-lens framework combining thematic coding, discourse interpretation, and vote-based prioritization.

### Lens 1 — Decision utility

Code each concept by the main decision or work function it supports.

Suggested codes:

- policy and planning
- operational response
- budgeting and investment
- local implementation
- risk communication
- research and modeling
- monitoring and reporting
- governance and standard-setting

This lens is grounded mainly in Question 1 outputs.

### Lens 2 — Service function

Code what kind of service the participant is actually imagining.

Suggested codes:

- dashboard
- map / GIS tool
- catalog / single source of truth
- API / data service
- raw dataset download
- early warning / forecast service
- methodology / guideline / manual
- integrated platform / clearinghouse
- analytical model / scenario engine
- reporting / workflow support tool

This lens is grounded mainly in Question 2 outputs.

### Lens 3 — Data and information requirements

Code the substantive inputs needed.

Suggested codes:

- hazard observations
- future climate projections
- exposure / asset data
- vulnerability / subgroup data
- loss and damage / impact data
- socio-economic / census / planning data
- metadata / dictionaries / standards
- interoperability / integration / API requirements
- endorsed baseline / official reference data

This lens distinguishes demand for more data from demand for more trustworthy and governable information.

### Lens 4 — Barriers and institutional friction

Code barriers from Question 3.

Suggested codes:

- fragmented ownership
- legal / PDPA / access restrictions
- lack of standards / inconsistent definitions
- weak metadata / poor interpretability
- low spatial resolution
- low temporal resolution / timeliness problems
- poor interoperability
- budget constraints
- staff capacity constraints
- lack of institutional mandate / weak authority
- uncertainty / credibility concerns

### Lens 5 — Priority profile

Keep sticker votes as separate fields:

- orange_score
- pink_score
- green_score

Interpretation:

- high orange = strong agency-specific fit
- high pink = broad shared relevance across actors
- high green = strong perceived suitability for DCCE’s early action

Optional derived fields may be added later, but only after preserving the original three-color distinctions.

## 7. Step-by-step workflow

### Phase 0 — Inventory and format audit

1. List all files in [`result/`](ψ/incubate/DCCE/CRDB/output/consultation_workshop/result/).
2. Tag each file as Markdown or Excel.
3. Determine whether each file contains Activity 1, Activity 2, or both.
4. Record the structure of each file:
   - tabular,
   - semi-structured narrative blocks,
   - mixed format.
5. Produce a source inventory note so future extraction remains traceable.

### Phase 1 — Raw extraction

1. Extract all Activity 2 concepts from each result file.
2. Preserve the original wording as much as possible.
3. For Excel files, capture worksheet names, column names, and any merged-cell structure before normalizing.
4. Do not interpret yet; focus on faithful extraction.

Output:
	- one raw extraction table with one row per service concept.

### Phase 2 — Normalization

1. Standardize field names across Markdown and Excel sources.
2. Separate combined cells such as “data + format” into distinct analytical fields where possible.
3. Normalize vote counts into numeric fields.
4. Normalize agency and category labels.
5. Keep a note whenever normalization required interpretation.

Output:
- a normalized Activity 2 master table.

### Phase 3 — Menu linkage analysis

1. Link each concept back to [`user_use_case_raw.md`](ψ/incubate/DCCE/CRDB/output/consultation_workshop/user_use_case_raw.md).
2. Identify whether participants:
   - selected a menu case intact,
   - translated it into sector-specific language,
   - merged multiple menu cases,
   - or introduced something new.
3. Record confidence and rationale.

This phase is critical because it reveals whether the interview-derived menu was usable and which areas needed stakeholder reframing.

### Phase 4 — Coding and interpretation

1. Apply the five-lens coding framework to each normalized concept.
2. Start with manual coding.
3. Allow emergent subcodes when repeated themes appear.
4. Add memo notes where participants blur “data,” “product,” “platform,” and “service.”

### Phase 5 — Descriptive summaries

Generate summaries such as:

- most common service functions,
- most common decision utilities,
- most common required data types,
- most common barriers,
- top concepts by orange, pink, and green votes,
- cross-tab: service function × barrier,
- cross-tab: agency type × service function,
- cross-tab: category × vote profile.

### Phase 6 — Discourse analysis layer

Following [`Qualitative-analysis-of-workshop-output.md`](ψ/incubate/DCCE/CRDB/inbox_note/Qualitative-analysis-of-workshop-output.md), analyze how participants talk about climate services.

Suggested discourse questions:

1. Do they frame climate services as data access, interpreted guidance, institutional endorsement, or platform integration?
2. Is risk framed as historical, projected, operational, or legal/administrative?
3. Who is imagined as responsible for provision, maintenance, validation, and decision support?
4. Where is the language confident, vague, skeptical, or dependent on authority?
5. Where do participants ask for usability and legitimacy rather than more raw data?

### Phase 7 — Strategic synthesis for CRDB

Translate findings into CRDB implications:

1. implications for Consultation Workshop Report,
2. implications for information product inventory,
3. implications for baseline data inventory,
4. implications for NCAIF design,
5. implications for governance / metadata / glossary / SSOT design,
6. implications for FGD3 ratification agenda,
7. implications for procurement-shield handoff and July 6 packaging.

## 9. Suggested quality controls

1. Every synthesis claim must point back to a source row/block.
2. Keep original Thai wording in the raw extraction layer.
3. Use normalized English labels only in coded fields, not as replacements for the source text.
4. Preserve ambiguous or partial records; do not over-clean them away.
5. Distinguish between:
   - stakeholder demand,
   - analyst interpretation,
   - CRDB strategic implication.
6. Do not collapse the three vote colors into a single score until the separate meanings have been analyzed.

## 11. Key analytical hypothesis

The central hypothesis to test is:

> Participants are not merely asking for more climate data. They are asking for climate services that combine usable formats, authoritative baselines, institutional trust, and actionable decision support.

The workshop analysis should therefore reveal not only which service concepts are desired, but also how stakeholders implicitly define a legitimate climate service for DCCE.
